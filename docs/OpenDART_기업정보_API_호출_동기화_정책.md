# OpenDART 기업정보 API 호출·동기화 정책

| 항목 | 내용 |
|---|---|
| 프로젝트 | FolioLens |
| 문서 유형 | 외부 API 연동 및 기업 기준정보 동기화 정책 |
| 문서 상태 | 초안 |
| 작성일 | 2026-07-27 |
| 적용 범위 | OpenDART 기업 고유번호 데이터와 `companies` 테이블 |
| 관련 요구사항 | CR-003, FR-001~003, FR-025~026, DR-001, DR-009, IR-002, NFR-SEC-001, NFR-MNT-001 |

## 1. 목적

이 문서는 OpenDART에서 기업 기준정보를 가져와 FolioLens의 기업 검색과 포트폴리오 종목 등록에 사용하는 방법을 정의한다.

핵심 목표는 다음과 같다.

- 사용자 검색 요청과 외부 API 호출을 분리한다.
- 기업정보를 내부 데이터베이스에 미리 저장해 빠르고 안정적으로 검색한다.
- 동일한 동기화 작업을 반복해도 데이터가 중복되거나 손상되지 않도록 한다.
- 외부 API 장애나 호출 제한이 사용자 기능 전체의 장애로 이어지지 않도록 한다.
- 인증키와 호출 기록을 안전하게 관리한다.

## 2. 적용 원칙

### 2.1 데이터 소스 우선순위

1. 대회에서 제공하는 기업·공시 데이터를 최우선으로 사용한다.
2. OpenDART는 대회 정책에서 외부 데이터 사용을 허용한 경우에만 사용한다.
3. 대회 데이터와 OpenDART를 함께 사용하는 경우 출처와 기준일을 구분해 저장한다.
4. 대회 정책이 확정되기 전에는 OpenDART 연동을 교체 가능한 외부 데이터 공급자로 구현한다.

### 2.2 사용자 검색과 외부 API 호출 분리

사용자가 기업을 검색할 때마다 OpenDART API를 호출하지 않는다.

```text
OpenDART 또는 대회 데이터
        ↓ 정기·수동 동기화
PostgreSQL companies 테이블
        ↓ 내부 DB 검색
기업 검색 API
        ↓
사용자
```

기업 검색 API는 PostgreSQL에 저장된 데이터만 조회한다. OpenDART 호출은 별도의 동기화 작업에서만 수행한다.

이 구조를 사용하는 이유는 다음과 같다.

- 검색 응답 속도가 외부 API 상태에 좌우되지 않는다.
- 인증키 노출 위험을 줄일 수 있다.
- 호출 제한을 불필요하게 소비하지 않는다.
- 개발·테스트 환경에서 실제 OpenDART 호출 없이 기능을 검증할 수 있다.

## 3. 인증키 관리 정책

### 3.1 저장

- 인증키는 환경변수 `OPENDART_API_KEY`로 주입한다.
- 인증키를 Java 코드, `application.yml`, 테스트 코드 또는 Git 저장소에 직접 작성하지 않는다.
- 로컬 개발에서 `.env`를 사용한다면 `.gitignore`에 포함한다.
- Docker Compose에서는 환경변수 참조 또는 별도 Secret 방식을 사용한다.
- 운영 환경에서는 배포 플랫폼의 Secret 관리 기능을 사용한다.

예시:

```yaml
opendart:
  api-key: ${OPENDART_API_KEY}
```

### 3.2 로그와 응답

- 요청 URL 전체에 인증키가 포함될 수 있으므로 전체 URL을 로그로 남기지 않는다.
- 인증키의 앞부분이나 뒷부분도 로그에 남기지 않는다.
- 예외 메시지, API 응답, 관리자 응답에 인증키를 포함하지 않는다.
- 인증키가 외부에 노출되면 기존 키를 폐기하거나 재발급하고 환경변수를 교체한다.

## 4. OpenDART 기업정보 수집 범위

### 4.1 기본 데이터

기업 기준정보 초기 적재에는 OpenDART의 고유번호 API를 사용한다.

```http
GET https://opendart.fss.or.kr/api/corpCode.xml?crtfc_key={OPENDART_API_KEY}
```

응답은 ZIP 파일이며, 압축 내부 XML에 다음 값이 포함된다.

| OpenDART 필드 | 의미 | 내부 필드 |
|---|---|---|
| `corp_code` | 공시대상회사의 고유번호 | `corpCode` |
| `corp_name` | 정식 회사명 | `corpName` |
| `corp_eng_name` | 영문 회사명 | 필요 시 확장 |
| `stock_code` | 상장회사 종목코드, 비상장사는 공백 | `stockCode` |
| `modify_date` | 최종 변경일 | 원천 데이터 변경 기준일 |

### 4.2 식별 기준

- `corpCode`를 기업 기준정보의 대표 외부 식별자로 사용한다.
- `corpCode`를 기준으로 기존 기업을 찾고 갱신한다.
- `stockCode`는 상장 여부와 종목 검색에 사용하지만 기업의 영구 식별자로 간주하지 않는다.
- `stockCode`가 공백이면 `null`로 저장하고 `listed=false`로 처리한다.
- `stockCode`가 존재하면 `listed=true`로 처리한다.
- 회사명이나 종목코드가 변경되어도 같은 `corpCode`라면 기존 기업정보를 갱신한다.

### 4.3 시장 구분

고유번호 API의 기본 응답만으로는 KOSPI, KOSDAQ, KONEX를 항상 확정할 수 없다.

- 별도의 신뢰할 수 있는 데이터가 없으면 시장 구분을 임의로 추정하지 않는다.
- 시장을 확인할 수 없는 경우 `OTHER` 또는 프로젝트에서 정의한 미확인 상태를 사용한다.
- 이후 대회 데이터 또는 허용된 공식 데이터로 시장 정보를 보완한다.

## 5. 동기화 정책

### 5.1 실행 시점

개발 환경:

- 초기에는 관리자가 명시적으로 실행하는 수동 동기화를 사용한다.
- 애플리케이션이 시작될 때 자동으로 전체 동기화를 실행하지 않는다.
- 테스트 실행 중에는 실제 OpenDART API를 호출하지 않는다.

운영·데모 환경:

- 수동 동기화 또는 하루 1회 새벽 시간대 동기화를 기본값으로 한다.
- 자동 실행이 필요하면 기본 스케줄은 매일 오전 3시(KST)로 한다.
- 대회 데이터 갱신 주기가 별도로 제공되면 그 주기를 우선한다.

### 5.2 동시 실행

- 전체 기업 동기화는 한 번에 하나만 실행한다.
- 이미 동기화가 실행 중이면 새로운 요청을 중복 실행하지 않는다.
- 다중 서버 환경에서는 DB 락 또는 분산 락으로 단일 실행을 보장한다.

### 5.3 전체 동기화 절차

1. 인증키 설정 여부를 확인한다.
2. 동기화 작업 시작 시각과 작업 ID를 기록한다.
3. OpenDART 고유번호 API를 한 번 호출한다.
4. ZIP 응답 여부와 HTTP 상태를 검증한다.
5. ZIP 압축을 해제하고 XML을 파싱한다.
6. 각 레코드의 필수값과 형식을 검증한다.
7. `corpCode`를 기준으로 신규·변경·동일 데이터를 구분한다.
8. 신규 기업은 추가하고 변경된 기업은 갱신한다.
9. 일정 크기의 배치로 데이터베이스에 반영한다.
10. 처리 건수와 실패 건수를 기록한다.
11. 모든 처리가 성공한 경우 마지막 성공 동기화 시각을 갱신한다.

### 5.4 저장 방법

- `corpCode` 기준 upsert 방식으로 저장한다.
- 동일한 데이터를 다시 동기화해도 중복 행이 생기지 않아야 한다.
- 권장 배치 크기는 500~1,000건이며 실제 성능 테스트 후 조정한다.
- 레코드 하나의 오류 때문에 전체 동기화를 즉시 중단하지 않고 실패 레코드 수와 원인을 집계한다.
- 필수 식별자인 `corpCode`가 없거나 형식이 잘못된 레코드는 저장하지 않는다.

### 5.5 삭제와 비활성화

- 한 번의 동기화 결과에서 기업이 보이지 않는다는 이유만으로 기존 행을 즉시 삭제하지 않는다.
- 외부 데이터 누락, 일시적 응답 오류 또는 데이터 제공 범위 변경 가능성을 고려한다.
- 상장폐지나 종목코드 소멸은 기업 자체 삭제와 구분한다.
- 상장 상태가 변경된 경우 기업정보는 유지하고 `stockCode`, `listed`, 유효기간 등의 상태만 갱신한다.
- 실제 삭제는 별도의 검증된 보존·삭제 정책이 마련된 후 수행한다.

### 5.6 트랜잭션

- 외부 API 호출과 ZIP 파싱은 긴 데이터베이스 트랜잭션 밖에서 수행한다.
- 검증이 끝난 데이터를 배치 단위의 짧은 트랜잭션으로 저장한다.
- 동기화 중 실패하더라도 기존에 정상 저장된 기업 검색 데이터는 유지한다.
- 외부 API 실패를 이유로 `companies` 테이블을 비우지 않는다.

## 6. API 호출 정책

### 6.1 타임아웃

초기 기본값은 다음과 같이 설정한다.

| 항목 | 기본값 |
|---|---:|
| 연결 타임아웃 | 5초 |
| 전체 응답 타임아웃 | 30초 |
| 최대 재시도 | 2회 |

타임아웃 값은 코드에 고정하지 않고 환경설정으로 관리한다.

### 6.2 재시도

재시도 대상:

- 일시적인 네트워크 연결 실패
- 연결 또는 응답 타임아웃
- OpenDART의 일시적인 5xx 응답
- 유지보수 등 일시적 장애로 판단되는 응답

재시도하지 않는 대상:

- 잘못되거나 등록되지 않은 인증키
- 사용이 중지된 인증키
- 허용되지 않은 요청 IP
- 잘못된 요청 파라미터
- 데이터 없음
- 요청 한도 초과
- ZIP 또는 XML 구조가 예상과 다르게 변경된 경우

재시도 간격에는 지수 백오프를 적용한다. 예를 들어 첫 실패 후 1초, 두 번째 실패 후 2초를 기다리되 운영 환경에서는 작은 무작위 지연을 추가할 수 있다.

### 6.3 호출 제한

- OpenDART의 호출 한도는 외부 정책에 따라 변경될 수 있으므로 코드에 특정 횟수를 전제로 구현하지 않는다.
- 요청 한도 초과 응답을 받으면 즉시 반복 호출하지 않는다.
- 해당 동기화 작업을 실패 또는 재시도 대기 상태로 기록한다.
- 사용자의 기업 검색 요청을 외부 호출로 연결하지 않는다.
- 전체 기업 목록은 고유번호 API의 일괄 다운로드 결과를 사용하고 기업별 반복 호출을 피한다.

## 7. 오류 처리

OpenDART 응답은 내부 도메인 오류로 변환한다.

| OpenDART 상황 | 내부 처리 | 자동 재시도 |
|---|---|---|
| 정상 응답 | ZIP·XML 검증 후 동기화 | 해당 없음 |
| 등록되지 않은 인증키 | 설정 오류 기록, 작업 중단 | 아니오 |
| 사용할 수 없는 인증키 | 인증키 상태 확인 안내 | 아니오 |
| 허용되지 않은 IP | 요청 IP 설정 확인 안내 | 아니오 |
| 데이터 없음 | 정상적인 빈 결과인지 API 오류인지 구분 | 아니오 |
| 요청 제한 초과 | `EXTERNAL_API_RATE_LIMITED`로 변환 | 즉시 재시도하지 않음 |
| OpenDART 점검·일시 장애 | 외부 서비스 장애로 기록 | 제한적으로 가능 |
| 네트워크·타임아웃 | 기존 DB 데이터 유지 | 최대 2회 |
| ZIP 손상·XML 파싱 실패 | 응답 형식 오류 기록, DB 반영 중단 | 아니오 |

실패 시 원칙:

- 기존 `companies` 데이터는 그대로 유지한다.
- 마지막 성공 동기화 시각을 갱신하지 않는다.
- 실패 작업의 작업 ID, 시각, 단계, 오류 유형을 기록한다.
- 인증키나 민감한 요청값은 오류 로그에 포함하지 않는다.

## 8. 기업 검색 API 정책

기업 검색 API는 동기화된 내부 DB만 조회한다.

예시:

```http
GET /api/v1/companies?query=삼성&listedOnly=true&page=0&size=20
```

검색 우선순위:

1. 종목코드 정확 일치
2. 정식 회사명 정확 일치
3. 회사명 부분 일치
4. 회사명 오름차순

`listedOnly`의 의미:

- `true`: 종목코드가 있는 상장 기업만 검색한다.
- `false`: 비상장 공시대상기업까지 검색 결과에 포함할 수 있다.
- FolioLens의 국내 상장 주식 포트폴리오 등록 화면에서는 기본값을 `true`로 사용한다.

외부 동기화가 실패해도 기존 기업정보를 이용한 검색은 계속 제공한다. 마지막 동기화 시각이 오래된 경우 운영 로그와 관리자 화면에서 확인할 수 있도록 한다.

## 9. 외부 데이터 공급자 분리

OpenDART에 도메인 로직이 직접 의존하지 않도록 공급자 인터페이스를 둔다.

예시:

```java
public interface CompanyMasterProvider {
    List<CompanyMasterData> fetchAll();
}
```

구현 예시:

- `OpenDartCompanyMasterProvider`: OpenDART API 호출
- `CompetitionCompanyMasterProvider`: 대회 제공 데이터 사용
- `FixtureCompanyMasterProvider`: 개발·테스트용 고정 데이터 사용

서비스 계층은 어떤 공급자를 사용했는지 알 필요 없이 정규화된 `CompanyMasterData`만 전달받는다.

## 10. 환경별 운영 정책

| 환경 | 데이터 공급자 | 동기화 방식 | 실제 OpenDART 호출 |
|---|---|---|---|
| 로컬 개발 | Fixture 또는 OpenDART | 기본 수동 | 명시적으로 실행할 때만 |
| 자동 테스트 | Fixture·Mock | 테스트별 고정 | 금지 |
| 개발 서버 | 대회 데이터 또는 OpenDART | 수동 또는 하루 1회 | 허용 범위에서만 |
| 평가 서버 | 대회 제공 데이터 우선 | 사전 적재 중심 | 대회 정책에 따름 |
| 운영·데모 | 승인된 공급자 | 수동 또는 하루 1회 | 승인된 경우만 |

## 11. 로그와 모니터링

기록할 항목:

- 동기화 작업 ID
- 데이터 공급자
- 시작·종료 시각
- 전체 소요 시간
- 읽은 레코드 수
- 신규 기업 수
- 갱신 기업 수
- 변경 없는 기업 수
- 검증 실패 수
- 저장 실패 수
- 동기화 성공·부분 성공·실패 상태
- 외부 API의 HTTP 상태와 내부 오류 코드
- 마지막 성공 동기화 시각

기록하지 않을 항목:

- OpenDART 인증키
- 인증키가 포함된 전체 요청 URL
- 불필요한 원문 응답 전체
- 사용자 포트폴리오 정보

권장 동기화 상태:

- `PENDING`
- `RUNNING`
- `COMPLETED`
- `PARTIAL`
- `FAILED`

## 12. 테스트 정책

### 12.1 단위 테스트

- 정상 ZIP과 XML 파싱
- 빈 `stockCode`를 `null`과 `listed=false`로 변환
- `corpCode` 기준 신규·갱신 판별
- 잘못된 필수 필드 거절
- 같은 입력을 반복했을 때 중복 행이 생성되지 않는지 확인
- 인증키와 요청 URL이 로그에 노출되지 않는지 확인

### 12.2 통합 테스트

- Mock 서버를 이용한 정상 응답 처리
- 타임아웃과 5xx 응답 재시도
- 인증 오류와 호출 제한 응답의 비재시도
- ZIP 손상과 XML 파싱 실패 시 기존 DB 보존
- 일부 레코드 실패 시 `PARTIAL` 상태와 처리 건수 확인
- 동시 동기화 요청이 하나만 실행되는지 확인

### 12.3 실제 API 확인

- 개발자가 명시적으로 실행하는 별도 테스트로 제한한다.
- 기본 자동 테스트와 CI에서는 실행하지 않는다.
- 실제 인증키가 없으면 테스트를 건너뛰도록 구성한다.
- 실제 API 테스트 결과를 저장소에 원문 그대로 커밋하지 않는다.

## 13. 완료 조건

다음 조건을 모두 만족하면 기업정보 동기화 기능이 완료된 것으로 본다.

1. 인증키가 환경변수로 관리된다.
2. OpenDART ZIP과 XML을 정상적으로 파싱한다.
3. `corpCode` 기준으로 기업정보를 멱등하게 저장한다.
4. 사용자 기업 검색은 외부 API 없이 내부 DB만 조회한다.
5. 외부 API 실패 시 기존 기업 데이터와 검색 기능이 유지된다.
6. 타임아웃, 제한된 재시도 및 오류 변환이 구현된다.
7. 동기화 결과와 마지막 성공 시각을 추적할 수 있다.
8. 자동 테스트에서 실제 OpenDART API를 호출하지 않는다.
9. 인증키가 코드, 로그, Git 이력에 노출되지 않는다.
10. 대회 제공 데이터와 OpenDART 중 사용할 공급자를 설정으로 교체할 수 있다.

## 14. 미결정 사항

1. 대회에서 OpenDART 사용을 허용하는 정확한 범위
2. 대회 제공 기업 기준정보의 필드와 갱신 주기
3. 운영 환경의 최종 동기화 주기
4. 시장 구분 데이터를 보완할 공식 데이터 소스
5. 회사명 변경 이력과 별칭을 별도 테이블로 관리할지 여부
6. 수동 동기화를 실행할 관리자 API 또는 운영 방식
7. 동기화 작업 이력을 별도 테이블로 저장할지 여부
