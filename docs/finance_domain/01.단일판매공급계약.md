# 공시 분석유형 01: 단일판매·공급계약

> 공통 적용 규격: [공시 분석유형 00: 공통 Fact·근거·계산·골든 규격](./공시_분석유형_00_공통규격.md)

| 항목 | 내용 |
|---|---|
| 문서 ID | `DISCLOSURE-ANALYSIS-01` |
| 내부 분석키 | `SUPPLY_CONTRACT` |
| 대상 | `exchange`의 단일판매공급계약체결 1,106건, 해지 20건과 관련 정정공시 |
| 목적 | 계약의 내용·금액·상대방·기간과 정정·해지 상태를 원문 근거로 답변 |

이 분석유형은 공식 대분류가 아니라 같은 Fact·계산·이력 규칙을 재사용하기 위한 FolioLens 내부 질문 대응 단위다.

데이터 기준으로 체결 1,106건과 해지 20건, 합계 1,126건이며 전체 4,204건의 26.78%, `exchange` 1,469건의 76.65%다. 체결공시 중 정정표시는 563건으로 관련 문서 합계의 50.00%다. 문서 수는 독립 계약 수가 아니며 하나의 계약에 여러 정정공시가 있을 수 있다.

## 1. 지원 질문

| ID | 질문 예시 | 필요한 Fact·처리 |

| `CON-Q03` | 외화 원금과 적용환율은? | 외화·환율 속성 |

`왜 해지됐어?`와 `해지금액·해지일은?`은 서로 다른 Fact를 요구하므로 같은 질문 유형으로 합치지 않는다.

### 질문 의도별 필수 Fact

| 질문 의도 | 필수 Fact | 조건부 Fact·계산 | 완료 기준 |
|---|---|---|---|
| 계약 핵심 | `contract.description`, `contract.amount`, `contract.counterparty`, `contract.start_date`, `contract.end_date` | 통화·VAT·금액성격 | 요청한 항목과 각 근거가 모두 확인됨 |
| 매출 대비 규모 | `contract.amount`, `contract.reference_sales`, `contract.disclosed_sales_ratio` | `CONTRACT_SALES_RATIO_CHECK` | 기간·연결기준·단위 검증 완료 |

| 해지 금액 | `contract.termination_amount` | 산정기준·이행금액 | 추정·잔여·확정 성격을 표시 |
| 최신 상태 | 최초공시와 기준시점까지의 확정 관계 | 정정·해지 이력 | 후보 관계를 최신값으로 사용하지 않음 |

## 2. 생성 방식 검수 기준

| 방식 | 이 유형에서의 의미 |
|---|---|
| `SOURCE_METADATA` | Manifest의 접수번호·접수일·공시명·정정 표시 |
| `DIRECT_RAW` | 원문 표·주석의 문자열을 그대로 추출 |
| `DIRECT_NORMALIZED` | 원문 하나의 날짜·숫자·단위·통화 형식만 통일 |
| `DERIVED_CLASSIFICATION` | 원문을 계약상태·금액성격 코드로 분류 |
| `DERIVED_CALCULATION` | 검증된 Fact로 비율·기간·증감을 계산 |
| `LINKED_RESOLVED` | 체결·정정·해지공시 관계를 근거로 확정 |

`contract.status`와 원계약 연결은 원문 한 칸에서 직접 얻지 않으므로 `DIRECT_NORMALIZED`가 아니다.

## 3. Fact 사전

이 문서의 의미 단위가 실제 `factKey`다. 표에서 설명 편의를 위해 붙인 `.raw`, `.value`, `.normalized_*`는 별도 factKey가 아니라 같은 Fact envelope의 `rawValue`, `rawUnit`, `normalizedValue`, `normalizedUnit` 속성에 대응한다. 원문과 정규화값의 생성 방식은 한 envelope 안에서도 각각 기록한다.

## 4. 계산과 해석

| 계산 ID | 공식 | 조건·의미 |
|---|---|---|
| `CONTRACT_SALES_RATIO_CHECK` | 계약금액÷기준매출액×100 | 동일 통화·단위·매출기간·연결기준 |
| `CONTRACT_DURATION_DAYS` | 종료일−시작일+1 | 양 끝 날짜 포함 규칙 표시 |
| `CONTRACT_AMOUNT_CHANGE` | 정정 후−정정 전 | 같은 금액성격일 때만 |
| `CONTRACT_AMOUNT_CHANGE_RATE` | 변화액÷정정 전×100 | 정정 전>0 |
| `CONTRACT_FX_CHECK` | 외화원금×공시환율 | 반올림 외화면 근사 검증 |

### 계산을 만든 이유와 답변 한계

| 계산 | 대응 질문 | 계산이 말해주는 것 | 의미하지 않는 것 |
|---|---|---|---|
| `CONTRACT_SALES_RATIO_CHECK` | 매출 대비 계약 규모가 맞아? | 공시가 사용한 기준매출 대비 계약금액의 상대적 크기 | 실제 매출 인식률·수익성 |
| `CONTRACT_DURATION_DAYS` | 계약기간은 며칠이야? | 예정 계약기간의 달력일수 | 실제 이행 완료기간 |
| `CONTRACT_AMOUNT_CHANGE_RATE` | 정정으로 계약금액이 얼마나 바뀌었어? | 같은 성격의 계약금액 증감률 | 변경의 긍정·부정 판단 |
| `CONTRACT_FX_CHECK` | 공시 원화 환산액이 맞아? | 공시 외화원금과 적용환율의 산술 검산 | 현재 환율 기준 가치 |

공시비율의 표시 자릿수를 우선한다. 계약금액을 확정매출, 해지금액을 확정손실로 표현하지 않는다.

비율 일치 판정은 고정 허용오차를 임의로 쓰지 않는다. 공시비율의 소수 자릿수를 `d`라 할 때 백엔드는 원계산값을 충분한 정밀도로 보존하고 `d`자리로 반올림한 표시값을 공시값과 비교한다. 원계산값 기준 허용범위는 원칙적으로 `0.5 × 10^-d %p` 이내이며, 부동소수점 오차가 아닌 십진수 연산을 사용한다.

## 5. 상태·근거

계약 사건 상태와 API 답변 상태를 분리한다.

| 구분 | 값 | 의미 |
|---|---|---|
| 계약 사건 상태 | `EXECUTED/CHANGED/TERMINATED/UNKNOWN` | 계약 자체의 기준시점 상태 |
| API 답변 상태 | `COMPLETED/PARTIAL/UNANSWERABLE/FAILED` | 사용자의 질문에 답한 완전성 |

- `asOf` 이전 체결·정정·해지만 반영한다.
- 숫자 근거는 셀 하나가 아니라 행 레이블·열 머리글·단위·주석을 포함한다.
- 정정 Fact는 정정 전·후 근거를 각각 보존한다.
- 관계가 후보뿐이면 계약상태를 확정하지 않고 `PARTIAL`로 답한다.
- 공시에 값이 없는 것은 `UNANSWERABLE`, 파서·검색·계산 실패만 `FAILED`다.

이 유형의 최소 evidence는 `receiptNo`, `documentRole`, `sectionPath`, `rowLabel`, `columnLabel`, `rawValue`, `rawUnit`, `sourceText`, `noteText`다. 해지공시에는 가능한 경우 원계약 접수번호의 관계근거도 필요하다.

## 6. 골든 후보

아래 사례는 회귀테스트 후보이며 아직 C의 최종 승인 전이다. 대회 제공 원문에서 값·단위·근거 위치를 다시 확인하고 승인한 뒤에만 고정 골든셋으로 승격한다.

### `GOLD-CONTRACT-001`

| 항목 | 기대값 |
|---|---|
| 회사·접수번호 | 삼성전자 `20250728800035` |
| 계약금액 | `22,764,764,160,000원` |
| 기준매출액 | `300,870,903,000,000원`, 2024년 연결 |
| 공시비율·재계산 | `7.6%`, `7.5662897053% → 7.6%` |
| 계약기간 | `2025-07-24`~`2033-12-31` |
| 관계 원문 | `-`이므로 `NOT_STATED` |
| 계약 사건 상태 | `EXECUTED`(체결공시 기준) |
| 기대 답변 상태 | 필요한 사실·근거가 모두 검증되면 `COMPLETED` |
| 승인 상태 | `C_REVIEW_PENDING` |

기대 원문 위치는 계약내용·계약금액·최근매출액·매출액대비·계약상대·계약기간의 각 표 행과 금액 산정 주석이다. 이 위치가 대회 원문에서 확인되기 전에는 고정 골든셋이 아니다.

### `GOLD-CONTRACT-CORR-001`

| 항목 | 기대값 |
|---|---|
| 회사·접수번호 | 삼성전자 `20250731800028` |
| 정정일 | `2025-07-31` |

| 변경 Fact | `contract.counterparty` |
| 정정 전 | 글로벌 대형기업 |
| 정정 후 | 테슬라(Tesla, Inc.) |
| `AS_FILED` | 원공시 상대방 반환 |

| 승인 상태 | `C_REVIEW_PENDING` |

정정표의 정정 전·후 열과 정정사유가 각각 근거다. 금액·기간까지 함께 변경하면 치명적 오류다.

### 골든 후보 공통 치명적 오류

- 계약금액과 해지금액 혼동
- 백만원·원 단위 오인
- 공시 기준매출액 대신 외부·최신 매출액 사용
- 정정 전후 상대방을 반대로 반환
- 해지금액을 확정손실, 계약금액을 확정매출로 표현
- 추정금액·VAT·환율 상태를 원문 없이 생성
- 원계약 관계가 후보인데 확정 연결
- 숫자에 표 행·단위·주석 근거를 연결하지 않음

## 7. B의 구현 순서

1. Manifest에서 체결·해지와 정정 후보를 라우팅한다.
2. 표 레이블·주석 동의어를 Fact ID에 매핑하고 `raw`를 먼저 반환한다.
3. 금액·단위·통화·날짜를 별도 필드로 정규화하되 원문을 덮어쓰지 않는다.
4. `-`·공란·비공개·미정을 서로 다른 결측코드로 처리한다.
5. 체결→정정→해지 관계를 원접수번호·관련공시·사건키로 확정한다.
6. `VERIFIED` Fact만 계산기에 전달한다.
7. C가 승인한 세 골든 후보의 추출 JSON·근거·계산을 회귀테스트한다.
8. 전체 1,126건의 `COMPLETED/PARTIAL/UNANSWERABLE/FAILED`와 미완료 원인 군집을 반환한다.
