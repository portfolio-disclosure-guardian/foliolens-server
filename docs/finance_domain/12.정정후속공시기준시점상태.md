# 공시 분석유형 12: 정정·후속공시 및 기준시점 상태

> 공통 적용 규격: [공시 분석유형 00: 공통 Fact·근거·계산·골든 규격](./공시_분석유형_00_공통규격.md)

## 1. 유형의 역할과 데이터 현황

유형 12는 독립된 경제 사건이 아니라 유형 01~11의 여러 문서를 하나의 사건으로 묶고, 사용자가 지정한 기준시점에 유효한 값과 상태를 결정하는 공통 계층이다. 제공 데이터 4,204건 중 정정 표시는 1,004건이다. 그룹별 정정은 거래소 공시 631건, 주요사항보고서 173건, 정기공시 159건, 대량보유 41건이다.

따라서 `is_correction=true`만 보고 원공시 전체를 덮어쓰면 안 된다. 정정 대상 Fact만 변경하고 원문 이력과 당시 상태를 보존해야 한다.

## 3. 핵심 용어

| 용어 | 뜻 | 예시 |
|---|---|---|
| 기준시점(`asOf`) | 답변에 포함할 정보의 시간상 마감일 | `asOf=2024-12-31`이면 2024-12-31까지 공개된 공시만 사용하고 이후 공시는 그 당시 답에서 제외 |
| Manifest | 한 사건을 구성하는 문서 목록, 관계, 적용 순서, 유효기간, 대표 Fact 버전을 기록한 사건 관리표 | 원공시→정정→완료 접수번호와 최신 상태 |
| 원공시 | 사건을 처음 알린 공시 | 계약체결·시설투자 결정 |
| 정정공시 | 기존 공시 일부를 변경·보완한 문서 | 계약금액·종료일 변경 |
| 후속공시 | 사건 진행·결과를 알리는 별도 공시 | 계약해지·취득결과·상장완료 |
| 관계 후보 | 같은 사건일 가능성은 있으나 확정 근거가 부족한 문서 관계 | 기업·유형·날짜만 유사 |

### 3.1 이 프로젝트의 실제 `manifest.jsonl`

대회에서 제공한 실제 Manifest는 `manifest.jsonl`이며, 4,204건의 공시를 한 줄에 한 문서씩 정리한 **원문 색인 파일**이다. `doc_id`, `corp_code`, `corp_name`, `stock_code`, `doc_group`, `doc_subtype`, `report_nm`, `is_correction`, `rcept_no`, `rcept_dt`, `file_path`, `file_format`, `n_files` 등을 통해 어떤 문서가 있고 원문이 어디에 있는지 알려준다.

이 파일만으로 투자금액·계약금액·정정 전후 값·원공시 관계를 모두 알 수는 없다. `is_correction=true`도 정정문서라는 후보정보일 뿐, 어떤 Fact가 바뀌었는지는 정정표 원문을 읽어야 한다.

### 3.2 이 문서의 `event_manifest`

아래 `event_manifest`는 대회 파일 `manifest.jsonl`과 다른 개념이다. 백엔드가 원문 색인을 바탕으로 결정·정정·완료·해지 문서를 같은 경제사건으로 묶기 위해 만드는 **사건별 문서·상태 관리구조의 권장 논리명**이다. 실제 클래스·테이블명은 B가 정하되, 대회 원문 Manifest와 이름·역할을 혼동하면 안 된다.

```text
대회 manifest.jsonl
→ 어떤 공시가 어디 있는지 찾는 문서 색인

event_manifest
→ 여러 공시가 같은 사건인지, 어떤 순서·상태인지 관리하는 파생 구조
```

## 4. 생성 방식·관계상태·입력출처 구분

세 종류를 한 열에 섞지 않는다.

### 4.1 Fact 생성 방식

| 코드 | 의미 |
|---|---|
| `DIRECT` | 정정표·본문·제목에 직접 있는 값 |
| `DIRECT_NORMALIZED` | 직접값을 날짜·금액·상태 코드로 변환한 값 |
| `DERIVED` | 변경액·변경률·상태 전이처럼 Fact로 계산한 값 |
| `LINKED` | 다른 접수번호 문서에서 관계를 확정해 가져온 값 |

실제 메타데이터에는 공통 규격의 `SOURCE_METADATA`, `DIRECT_RAW`, `TEXT_EXTRACTED`, `DIRECT_NORMALIZED`, `DERIVED_CLASSIFICATION`, `DERIVED_CALCULATION`, `LINKED_RESOLVED`, `SYSTEM_ASSIGNED`를 사용한다. 이 절의 `DIRECT` 등은 설명용 축약이다.

### 4.2 문서 관계의 확신 상태

| 코드 | 의미 | 사용 조건 |
|---|---|---|
| `CONFIRMED_LINK` | 같은 사건 관계가 확정됨 | 원공시 접수번호, 정정표, 관련공시란, 사건번호 등 명시 근거 |
| `CANDIDATE_LINK` | 관계 후보지만 확정 근거가 부족함 | 기업·유형·날짜·대상만 유사 |
| `REJECTED_LINK` | 검토 결과 다른 사건임 | 상대방·대상·원공시번호 불일치 |

`CANDIDATE_LINK`는 Fact 생성 방식이 아니다. 후보 문서의 값을 최신 Fact로 사용하지 않고 추가 확인 대상으로만 남긴다.

### 4.3 입력 출처

| 코드 | 의미 | 예시 |
|---|---|---|
| `DISCLOSURE_INPUT` | 공시에서 들어온 값 | 계약금액, 결정일 |
| `QUERY_INPUT` | 사용자 질문에서 들어온 검색 조건 | 회사명, `asOf=2024-12-31` |
| `SYSTEM_INPUT` | 시스템 실행시각·정책 버전 등 | 계산정책 버전 |

`QUERY_INPUT`도 생성 방식이 아니다. 특히 `asOf`는 공시 Fact가 아니라 “그 날짜 이후 공시를 당시 답변에서 사용하지 말라”는 조회 조건이다.

`asOf=2024-12-31`은 “2024년 12월 31일 현재를 기준으로 답변한다”는 뜻이다. 이후 공시를 삭제한다는 뜻이 아니라 그 질문의 과거시점 답변에서만 제외한다. 날짜가 없는 “현재” 질문은 대회 데이터의 최신 허용시점을 적용하고 그 기준시점을 답변에 표시한다.

## 5. Manifest와 Fact 사전

유형 01~11의 실제 Fact는 프로젝트 공통 envelope(`factKey`, `rawValue`, `rawUnit`, `normalizedValue`, `normalizedUnit`, `evidenceIds`, `validationStatus`)를 사용한다. 아래 Manifest·버전 필드는 그 Fact들을 시간순으로 연결하는 관리 구조이며 원문 Fact 계약을 대체하지 않는다.

### 5.1 사건 Manifest

| Fact/필드 ID | 의미 | 생성 | 근거·조건 |
|---|---|---|---|
| `event_manifest.event_id` | 동일 경제 사건에 부여한 내부 식별자 | `SYSTEM_ASSIGNED` | 기업·유형 안에서 유일 |
| `event_manifest.domain_type` | 유형 01~11 중 해당 분석유형 | `DERIVED_CLASSIFICATION` | 제목·서식·manifest 분류를 종합 |
| `event_manifest.entity_id` | 공시회사 표준 식별자 | `SOURCE_METADATA` | 대회 manifest의 회사코드 |
| `event_manifest.entity_name` | 공시회사 원문명 | `SOURCE_METADATA` | 대회 manifest의 회사명 |
| `event_manifest.root_receipt_no` | 사건의 최초 원공시 접수번호 | 원문에 번호가 있으면 `DIRECT_RAW`, 탐색해 확정하면 `LINKED_RESOLVED` | 정정표 원공시일·관계근거 |
| `event_manifest.documents[].receipt_no` | 사건에 포함된 각 문서 접수번호 | `SOURCE_METADATA` | 대회 manifest의 접수번호 |
| `event_manifest.documents[].document_date` | 각 문서 공시일시 | 원문은 `SOURCE_METADATA`, 표준시각은 `DIRECT_NORMALIZED` | 접수일시 |
| `event_manifest.documents[].document_role.raw` | 원공시·정정·완료·해지·철회 등 역할 원문 | `SOURCE_METADATA` 또는 `DIRECT_RAW` | 제목·정정표·서식 |
| `event_manifest.documents[].document_role.code` | 문서 역할 표준 코드 | `DIRECT_NORMALIZED` | 역할 원문 매핑 |
| `event_manifest.documents[].link_status` | 다른 문서와의 관계 확신 상태 | 관계근거로 판정한 `DERIVED_CLASSIFICATION`; 관계상태 메타데이터이며 공시 직접 Fact가 아님 | `CONFIRMED_LINK` 등 |
| `event_manifest.documents[].link_evidence` | 관계를 판단한 근거 | `DIRECT_RAW`, `SOURCE_METADATA` 또는 `LINKED_RESOLVED` | 원공시 접수번호·관련공시명·사건번호 |
| `event_manifest.current_status.raw` | 기준시점 최신 근거문서의 상태 원문 | 해당 문서의 `DIRECT_RAW`를 `LINKED_RESOLVED`로 선택 | 기준시점까지의 최신 상태문구 |
| `event_manifest.current_status.code` | 상태 전이 규칙으로 정한 현재 상태코드 | `DERIVED_CLASSIFICATION` | 상태 전이 규칙 적용 |
| `event_manifest.status_as_of` | 현재 상태를 계산한 기준시각 | 값 출처 `QUERY_INPUT`; Fact 생성 방식 아님 | 공시 Fact가 아닌 조회 메타데이터 |
| `event_manifest.policy_version` | 적용한 연결·정정·상태 정책 버전 | 값 출처 `SYSTEM_INPUT`; 생성은 `SYSTEM_ASSIGNED` | 재현성을 위해 기록 |

### 5.2 정정 기본 Fact

| Fact ID | 의미 | 생성 | 원문 근거·조건 |
|---|---|---|---|
| `correction.is_correction` | 문서가 정정공시인지 | manifest 직접값은 `SOURCE_METADATA`, 제목·정정표 판정은 `DERIVED_CLASSIFICATION` | 출처를 구분 |
| `correction.date` | 정정 제출일 | 원문은 `SOURCE_METADATA`, 표준날짜는 `DIRECT_NORMALIZED` | 접수일시 |
| `correction.original_disclosure_date` | 정정 대상 원공시일 | `DIRECT_NORMALIZED` | 정정표 |
| `correction.original_receipt_no` | 정정 대상 원공시 접수번호 | 명시값은 `DIRECT_RAW`, 탐색값은 `LINKED_RESOLVED` | 명시 접수번호 우선 |
| `correction.reason` | 정정 사유 원문 | `DIRECT_RAW` | 정정표의 정정사유 |
| `correction.scope[].raw` | 정정 대상 항목 원문 | `DIRECT_RAW` | 실제 정정표에서 확인된 영역만 |
| `correction.scope[].code` | 정정 영역 표준 코드 | `DIRECT_NORMALIZED` | 정정항목 원문 매핑 |
| `correction.changes[].fact_id` | 변경된 원문 항목에 대응하는 도메인 Fact ID | `DERIVED_CLASSIFICATION` | 원문 항목과 Fact 사전 매핑 |
| `correction.changes[].before.raw` | 정정 전 원문값 | `DIRECT_RAW` | 정정 전 열 |
| `correction.changes[].after.raw` | 정정 후 원문값 | `DIRECT_RAW` | 정정 후 열 |
| `correction.changes[].before.normalized` | 정정 전 표준값 | `DIRECT_NORMALIZED` | 단위·날짜 확정 시 |
| `correction.changes[].after.normalized` | 정정 후 표준값 | `DIRECT_NORMALIZED` | 같은 기준으로 변환 |
| `correction.changes[].effective_from` | 정정 후 값이 유효하다고 보는 시점 | 원문 명시면 `DIRECT_NORMALIZED`, 아니면 `SYSTEM_ASSIGNED` 정책값 | 소급 여부·정정일 정책 기록 |
| `correction.changes[].evidence_locator` | 정정표의 표·행·문장 위치 | `SYSTEM_ASSIGNED` | 원문 좌표 |

### 5.3 기준시점 Fact 버전

| 필드 ID | 의미 | 생성 | 조건 |
|---|---|---|---|
| `fact_version.fact_id` | 버전을 관리하는 Fact | `SYSTEM_ASSIGNED` | 유형별 Fact ID |
| `fact_version.value.raw` | 해당 버전의 원문값 | 원 Fact의 `DIRECT_RAW` 방식 승계 | 원문값 삭제 금지 |
| `fact_version.value.normalized` | 해당 버전의 표준값 | 원 Fact의 `DIRECT_NORMALIZED`, `DERIVED_CLASSIFICATION`, `DERIVED_CALCULATION` 방식 승계 | 변환근거 기록 |
| `fact_version.valid_from` | 이 버전이 적용되기 시작하는 시점 | 원문 명시면 `DIRECT_NORMALIZED`, 아니면 `SYSTEM_ASSIGNED` 정책값 | 정정·완료 시점 |
| `fact_version.valid_to` | 다음 버전 전까지의 종료시점 | `SYSTEM_ASSIGNED` | 다음 유효버전 시작경계로 설정; 금융 계산값 아님 |
| `fact_version.source_receipt_no` | 이 값을 제공한 공시 | `SOURCE_METADATA` | 접수번호 |
| `fact_version.supersedes_version_id` | 대체한 이전 버전 | `SYSTEM_ASSIGNED` 관계 메타데이터 | 변경된 같은 Fact에만 |
| `fact_version.is_current` | 최신 기준 유효 버전 여부 | `DERIVED_CLASSIFICATION` | 기준시점에 따라 달라짐 |

### 5.4 문서 역할·조회모드 코드

| 코드 집합 | 코드 | 의미 |
|---|---|---|
| 문서역할 | `ORIGINAL` | 사건을 최초로 알린 원공시 |
| 문서역할 | `CORRECTION` | 기존 문서 일부를 정정·보완 |
| 문서역할 | `PROGRESS` | 진행상황을 알리는 후속공시 |
| 문서역할 | `COMPLETION` | 실제 완료·결과를 알리는 공시 |
| 문서역할 | `TERMINATION` | 해지·철회·취소·중단을 알리는 공시 |
| 문서역할 | `RESULT` | 취득결과·판결 등 결과공시 |
| 문서역할 | `UNKNOWN` | 역할 확인불가 |
| 조회모드 | `AS_FILED` | 선택한 공시가 제출됐을 당시 그 문서의 값만 봄 |
| 조회모드 | `LATEST_AS_OF` | `asOf`까지 공개된 확정관계 문서의 최신 유효값을 봄 |
| 조회모드 | `FULL_HISTORY` | 원공시부터 모든 정정·후속 버전을 시간순으로 봄 |

정정범위 코드는 모든 유형에 똑같은 폐쇄형 목록 하나를 강요하지 않는다. 공통 범위 `FINANCIAL_STATEMENT`, `FINANCIAL_NOTE`, `BUSINESS_INFORMATION`, `AUDIT_INFORMATION`, `GOVERNANCE`, `SHAREHOLDING`, `TYPOGRAPHICAL`, `OTHER`, `UNKNOWN`과 각 유형 문서의 전용 범위를 함께 사용한다. 범위코드는 변경영역 분류이고 실제 변경값은 `changes[].fact_id`가 가리킨다.

## 6. 문서 연결 규칙

연결은 다음 강도 순서로 판정한다.

1. 원공시 접수번호가 명시됨 → `CONFIRMED_LINK`.
2. 정정표에 원공시일·공시명이 명시되고 회사·유형·대상이 일치 → `CONFIRMED_LINK`.
3. 관련공시란·사건번호·계약 식별자가 일치 → `CONFIRMED_LINK`.
4. 회사·유형·상대방·대상·날짜만 유사 → `CANDIDATE_LINK`; 자동 병합 금지.
5. 명시 식별자가 충돌 → `REJECTED_LINK`.

문서 관계유형은 다음처럼 의미를 분리한다.

| 관계유형 | 의미 |
|---|---|
| `ORIGINAL_TO_CORRECTION` | 원공시와 그 일부를 바꾸는 정정공시 |
| `DECISION_TO_PROGRESS` | 결정공시와 진행 후속공시 |
| `DECISION_TO_COMPLETION` | 결정공시와 실제 완료공시 |
| `DECISION_TO_TERMINATION` | 결정공시와 해지·철회·취소공시 |
| `PROCEEDING_TO_RESULT` | 소송·행정절차와 판결·결과공시 |
| `SAME_SECURITY_MARKET_TRANSFER` | 동일 증권의 기존시장 폐지와 신규시장 상장 |
| `RELATED_BUT_INDEPENDENT` | 경제적으로 관련되지만 하나가 다른 하나를 정정·대체하지 않는 별도 사건 |
| `UNKNOWN` | 관계유형 확인불가 |

`CANDIDATE_LINK` 예시는 같은 회사·공시유형·근접한 날짜지만 원공시 번호·정정표·사건번호가 없는 경우다. 후보는 재탐색 목록에는 남기되 값 병합·상태 전이·최신값 선택에는 쓰지 않는다.

정기보고서의 재작성·정정은 재무제표, 주석, 사업정보, 감사정보, 지배구조, 지분정보, 단순오류 중 실제 범위를 먼저 판정한다. `is_correction=true`만으로 모든 재무값을 변경하지 않는다.

## 7. 상태 전이 규칙

| 현재 상태 | 후속 근거 | 새 상태 | 주의 |
|---|---|---|---|
| `DECIDED` | 실제 개시·계약 이행 근거 | `IN_PROGRESS` | 예정일 도래만으로 전이 금지 |
| `DECIDED/IN_PROGRESS` | 완료·결과공시 | `COMPLETED` | 일부 완료는 `PARTIALLY_COMPLETED` |
| 진행 상태 | 공식 해지·철회·취소 | `TERMINATED/CANCELLED` | 정정만으로 취소 처리 금지 |
| 법률절차 진행 | 확정판결·확정처분 | `FINAL` | 1심 판결을 자동 확정 금지 |
| 어떤 상태든 | 근거 Fact 일부 누락 | 상태 유지 + 답변 `PARTIAL` | 사건 상태와 답변 상태 구분 |

사건 상태와 API 답변 상태는 다르다. 사건이 `IN_PROGRESS`여도 질문에 필요한 모든 사실을 답하면 API는 `COMPLETED`일 수 있다.

## 8. 계산·변경 규칙

| 계산 ID | 공식 | 조건 |
|---|---|---|
| `VALUE_CHANGE` | `정정 후 값 − 정정 전 값` | 같은 Fact·단위 |
| `VALUE_CHANGE_RATE` | `(정정 후 값 − 정정 전 값) ÷ 정정 전 값 × 100` | 정정 전 값이 0이 아님 |
| `DATE_CHANGE_DAYS` | `정정 후 날짜 − 정정 전 날짜` | 같은 일정 의미 |
| `RATIO_CHANGE_PP` | `정정 후 비율 − 정정 전 비율` | 같은 분모·백분율 기준 |
| `AS_OF_VALUE_SELECT` | `valid_from ≤ asOf < valid_to`인 버전 선택 | 시간대·경계정책 통일 |

비율 검증은 공시의 표시 자릿수를 기준으로 한다. 공시값이 소수 `d`자리면 원계산값을 같은 자리로 반올림해 비교하고, 원계산값 기준 허용범위는 원칙적으로 `0.5 × 10^-d %p` 이내로 둔다. 십진수 연산을 사용하며 유형마다 근거 없는 고정 허용오차를 만들지 않는다.

정정 전후 문자열이 달라도 정규화값이 같으면 표현 정정일 수 있다. 반대로 단위가 바뀌었으면 원문 비교가 아니라 정규화 후 의미상 변경을 판정한다.

### 8.1 계산을 만든 이유와 결과 범위

| 대응 질문 | 계산 | 이유 | 말할 수 있는 것 | 말하면 안 되는 것 |
|---|---|---|---|---|
| 금액이 얼마나 바뀌었어? | `VALUE_CHANGE`, `VALUE_CHANGE_RATE` | 같은 Fact의 변경 크기 표현 | 증감액·증감률 | 변화가 긍정·부정이라는 단정 |
| 일정이 며칠 바뀌었어? | `DATE_CHANGE_DAYS` | 같은 일정의 날짜차이 표현 | 연장·단축일수 | 지연 원인·실패 단정 |
| 지분율이 얼마나 바뀌었어? | `RATIO_CHANGE_PP` | 비율 자체의 차이를 %p로 표현 | 퍼센트포인트 변화 | 상대 변화율과 혼용 |
| 그 날짜 당시 값은? | `AS_OF_VALUE_SELECT` | 과거 시점의 유효버전 재현 | 그 시점까지 공개된 값 | 이후 결과를 과거에 소급 |

`AS_OF_VALUE_SELECT`는 금융 산술식이라기보다 시간구간 선택 규칙이다. 동일 접수시각 경계에서 해당 문서를 포함할지, 날짜만 입력된 경우 장 마감·일 종료를 어떻게 볼지는 정책버전으로 고정한다.

### 8.2 계산·선택 불가 조건

- 관계가 `CANDIDATE_LINK`뿐이면 정정·후속값을 선택하지 않는다.
- before/after가 같은 Fact·단위·기준이 아니면 변화율을 계산하지 않는다.
- 정정 전 값이 0이면 변화율을 계산하지 않고 변화액만 제시한다.
- 비율의 분모·주식종류가 달라지면 단순 %p 비교를 중단한다.
- 종료일 변경과 계약 해지를 같은 상태전이로 취급하지 않는다.
- 기준시점 이후 문서를 현재 알고 있다는 이유로 과거 답변에 포함하지 않는다.

## 9. 답변 상태 판정

| API 상태 | 기준 |
|---|---|
| `COMPLETED` | 질문에 필요한 Fact, 기준시점, 원문 근거와 필요한 계산이 모두 검증됨 |
| `PARTIAL` | 일부 Fact·후속공시·근거가 누락됐지만 확인된 범위의 답변 가능 |
| `UNANSWERABLE` | 제공 데이터·허용 데이터 안에 핵심 답이 없거나 기준시점 문서를 특정할 수 없음 |
| `FAILED` | 데이터 부족이 아니라 파싱·조회·계산·서비스 오류로 처리가 중단됨 |

관계가 `CANDIDATE_LINK`뿐이면 이를 최신값에 반영하지 않고 “관련 가능성이 있으나 동일 사건 여부 추가 확인 필요”라고 답한다.

## 10. 골든 후보

아래 사례는 유형별 문서연결 회귀테스트의 `C 검토대기` 후보다. 명시적 원공시번호·정정표·공식 완료공시로 관계를 확정한 뒤 고정한다.

### GOLD-CORRECTION-001: 계약 원공시→정정

- 원공시 접수번호: 삼성전자 공급계약 `20250728800035`
- 정정공시 접수번호: `20250731800028`
- 기대: 두 문서를 `CONFIRMED_LINK`로 연결하고 정정표에 실제 기재된 Fact만 before/after 버전으로 만든다.
- `asOf` 검증: 정정공시 전 날짜로 조회하면 원공시 버전, 정정공시 후 날짜로 조회하면 정정 후 버전을 반환한다.
- 치명적 오류: 정정되지 않은 필드까지 새 버전 생성, 원문값 삭제, 두 문서를 별도 계약으로 생성.

### GOLD-CORRECTION-002: 결정→완료

- 삼성전자 해외상장 결정 `20241031000536`
- 삼성전자 해외상장 완료 `20250213001817`
- `asOf=2024-12-31`: `DECIDED` 또는 당시 확인된 진행상태. 2025-02-13 완료공시는 당시 답변에서 제외한다.
- `asOf=2025-02-13` 완료공시 시각 이후: 완료 근거가 반영된 `event_status=COMPLETED`. 같은 시각 경계에서는 접수시각 포함 정책을 적용한다.
- 치명적 오류: 현재 알고 있는 완료 결과를 과거 기준시점 답변에 소급해 사용.

### GOLD-CORRECTION-003: 정기공시 부분 정정

- 대상: LG이노텍 반기보고서 정정 `20240913000803`
- 기대: 정정 대상 영역을 확인해 해당 Fact만 갱신한다.
- 치명적 오류: 정정 플래그만 보고 모든 재무제표 수치를 변경 또는 무효화.

### GOLD-CORRECTION-004: 후보 관계 병합 금지

- 입력: 같은 기업·유형·근접한 날짜의 원공시 후보가 있으나 정정표·원공시 번호·사건번호가 없는 상황.
- 기대 관계상태: `CANDIDATE_LINK`.
- 기대 처리: 후보 문서 Fact를 최신값에 반영하지 않고 `추가 확인 필요`를 반환.
- 기대 API 상태: 핵심 답변이 후보 관계에 의존하면 `PARTIAL` 또는 `UNANSWERABLE`; 검색·파싱 자체가 정상이라면 `FAILED`가 아님.
- 치명적 오류: 날짜·기업만 같다는 이유로 `CONFIRMED_LINK`로 승격.

### GOLD-CORRECTION-005: 해지 사건의 상태와 답변상태 분리

- 대상 후보: 공급계약 또는 구조개편의 결정→해지·계약해제 공시.
- 기대 사건상태: `TERMINATED` 또는 유형상 `CANCELLED`.
- 기대 API 상태: 해지 사실·사유·기준시점·근거가 완전하면 `COMPLETED`.
- 치명적 오류: 사건이 종료됐다는 이유로 API `FAILED` 반환.

### 10.1 공통 치명적 오류

1. 대회 `manifest.jsonl`과 파생 `event_manifest`를 같은 파일·개념으로 취급.
2. `is_correction=true`만으로 원공시 모든 Fact를 덮어씀.
3. 정정 전 원문값과 근거를 삭제.
4. 원공시·정정·완료·해지를 서로 다른 독립사건으로 무조건 생성.
5. `CANDIDATE_LINK`를 확정관계로 사용해 최신값 병합.
6. 명시 식별자 충돌에도 관계를 유지.
7. 기준시점 이후 공시를 과거 답변에 소급 반영.
8. `AS_FILED`, `LATEST_AS_OF`, `FULL_HISTORY`를 구분하지 않음.
9. 예정일 도래만으로 완료 상태 부여.
10. 정정과 해지·철회·완료를 같은 문서역할로 처리.
11. 사건상태 `TERMINATED/FAILED`와 API 답변상태 `FAILED`를 혼동.
12. 데이터 부족을 시스템 오류 `FAILED`로 처리하거나 시스템 오류를 `UNANSWERABLE`로 숨김.
13. 값·단위·기준이 다른 정정 전후 수치를 직접 계산.
14. 사용자 질문의 `asOf`를 공시에서 추출한 금융 Fact로 취급.
15. 정책버전·선택 근거 없이 최신값만 반환해 과거 답변을 재현할 수 없게 함.

## 11. B의 구현 순서

1. 모든 문서에 접수번호·회사·유형·공시일시·정정 여부를 먼저 부여한다.
2. 명시적 원공시번호와 정정표를 최우선으로 사건 Manifest를 만든다.
3. 정정 전후 원문을 도메인 Fact ID에 매핑하고 원문·정규화 버전을 모두 저장한다.
4. 완료·해지·철회·판결 등 후속공시를 확정근거가 있을 때만 연결한다.
5. 기준시점(`asOf`) 선택기를 구현해 그 시점 이후 문서를 제외한다.
6. 유형별 상태 전이표를 적용하되 예정일 도래만으로 완료하지 않는다.
7. 계산·답변에는 선택된 Fact 버전의 접수번호와 원문 근거를 전달한다.
8. C가 승인한 다섯 골든 후보로 정정 범위, 과거시점 재현, 결정→완료, 후보 병합 금지, 사건상태/API 상태 분리를 회귀검증한다.
