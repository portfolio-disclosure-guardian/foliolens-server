# 공시 분석유형 00: 공통 Fact·근거·계산·골든 규격

| 항목 | 내용 |
|---|---|
| 문서 ID | `DISCLOSURE-ANALYSIS-COMMON` |
| 적용 범위 | 공시 분석유형 01~12 전체 |
| 문서 목적 | 유형별 Fact와 계산을 같은 기준으로 구현·검수하기 위한 공통 계약 |
| 사용 주체 | C: 금융정책·골든 승인, B: 추출·정규화·계산·이력 구현, A: 질문 실행·답변·API 통합 |

이 문서는 유형별 문서에 반복되는 기술·검수 규칙의 단일 기준이다. 각 유형 문서는 이 규격에 더해 해당 유형의 질문, Fact 의미, 원문 위치, 계산 조건과 골든 후보를 정의한다. 서로 충돌하면 프로젝트 승인 명세와 해당 유형에서 더 구체적으로 정한 규칙을 우선한다.

## 1. 질문과 Fact의 관계

질문 예시는 평가 질문 문장을 모두 미리 열거하기 위한 목록이 아니다. 질문 의도를 유한한 Fact와 계산으로 연결하기 위한 라우팅 사례다.

```text
사용자 질문
→ 기업·기간·asOf·공시유형·의도 후보 생성
→ 백엔드가 기업·기간·enum 검증
→ 필요한 Fact ID 선택
→ 검증된 Fact 우선 조회
→ 부족한 서술형 Fact만 원문 evidence에서 추출
→ 정정·후속 이력 해결
→ 필요한 계산만 결정적 로직으로 실행
→ 사실·계산·설명·한계를 구분해 답변
```

질문 예시에 없는 표현이 들어와도 같은 의도와 Fact 조합으로 매핑되면 처리할 수 있다. 반대로 필요한 Fact가 없으면 비슷한 질문 예시가 있더라도 값을 추정하지 않는다.

## 2. Fact ID와 공통 envelope

`facility.amount`, `contract.amount`처럼 금융적으로 하나의 의미를 갖는 이름이 실제 `factKey`다. `.raw`, `.value`, `.normalized`는 별도의 금융 Fact ID가 아니라 같은 Fact의 저장 속성을 설명하는 논리 표기다.

모든 Fact는 다음 envelope를 사용한다.

| 속성 | 의미 | 필수 조건 |
|---|---|---|
| `factKey` | 유형 문서가 승인한 의미 단위 식별자 | 필수 |
| `valueType` | `TEXT/DECIMAL/INTEGER/DATE/BOOLEAN/CODE/LIST` 등 자료형 | 필수 |
| `rawValue` | 원문에 표시된 값·문장 | 직접·텍스트 추출 Fact에 필수 |
| `rawUnit` | 원·천원·백만원·주·% 등 원문 단위 | 수치 Fact에 필수 |
| `normalizedValue` | 형식·단위 변환 또는 승인 코드 값 | 정규화 가능한 경우 |
| `normalizedUnit` | `KRW`, `SHARE`, `PERCENT`, ISO 날짜 등 표준단위 | 정규화 가능한 경우 |
| `currency` | 원문 금액 통화 | 금액 Fact에 필수 |
| `periodStart/periodEnd` | 값이 측정된 기간 | 기간형 재무 Fact에 필수 |
| `asOfDate` | 잔액·상태가 유효한 기준일 | 시점형 Fact에 필수 |
| `accountingBasis` | 연결·별도·기타 기준 | 재무·비율 Fact에 필수 |
| `generationMethod` | 아래 생성 방식 | 필수 |
| `availabilityStatus` | 아래 결측 상태 | 필수 |
| `validationStatus` | `UNVALIDATED/VERIFIED/REJECTED` | 필수 |
| `evidenceIds` | 원문 근거 식별자 | 직접·정규화·분류 Fact에 필수 |
| `sourceReceiptNo` | Fact를 제공한 접수번호 | 필수 |
| `policyVersion` | 정규화·분류·계산 규칙 버전 | 정규화·파생 Fact에 필수 |

원문값은 정규화값으로 덮어쓰지 않는다. 예를 들어 원문 `5,296,200`과 단위 `백만원`을 보존하면서 정규화값 `5,296,200,000,000`, 단위 `KRW`를 함께 저장한다.

## 3. 생성 방식 전수검수 기준

| 생성 방식 | 정의 | 허용 예 | 금지 예 |
|---|---|---|---|
| `SOURCE_METADATA` | 대회 Manifest에서 직접 받은 메타데이터 | 접수번호·접수일·`is_correction` | Manifest에 없는 원공시 관계 추정 |
| `DIRECT_RAW` | 명시된 표 행·셀·제목에서 원문값을 직접 읽음 | 투자금액 행, 계약상대방 행 | 문맥을 해석해 만든 상태코드 |
| `TEXT_EXTRACTED` | 서술형 문장에서 해당 사실 구간을 추출 | 투자목적, 해지 배경, 소송 대응 | 원문에 없는 사유 생성 |
| `DIRECT_NORMALIZED` | 하나의 직접값을 의미 변경 없이 형식·단위·승인 동의어로 변환 | `2024.04.24`→`2024-04-24`, 백만원→원 | 여러 문서를 합쳐 현재 상태 결정 |
| `DERIVED_CLASSIFICATION` | 하나 이상의 원문 근거를 승인 규칙으로 상태·성격 코드화 | `수령 예정`→`PAYMENT_EXPECTED` | 제목만 보고 실제 수령 확정 |
| `DERIVED_CALCULATION` | 검증된 입력 Fact와 공식으로 새 숫자를 계산 | 투자금액÷자기자본 | LLM이 답변 중 암산 |
| `LINKED_RESOLVED` | 원접수번호·정정표·관련공시 등으로 다른 문서 관계를 확정 | 결정→완료, 체결→해지 | 기업·날짜가 비슷하다는 이유만으로 연결 |
| `SYSTEM_ASSIGNED` | 시스템 내부 식별자·버전 | 사건 ID, Fact 버전 ID | 공시 사실처럼 사용자에게 제시 |

`CANDIDATE_LINK`, `QUERY_INPUT`, `SYSTEM_INPUT`은 Fact 생성 방식이 아니다. 각각 관계의 확신 상태, 사용자 조회조건, 실행 메타데이터다.

### 3.1 정규화 처리유형

생성 방식과 별도로 B가 어떤 후처리를 해야 하는지 다음 처리유형을 기록할 수 있다.

| 처리유형 | 의미 | 예 |
|---|---|---|
| `PASSTHROUGH` | 원문 의미를 바꾸지 않고 보존 | 계약목적·정정사유 |
| `FORMAT` | 날짜·문자열 형식만 통일 | `2025년 3월 1일`→`2025-03-01` |
| `UNIT` | 승인된 단위로 환산 | 백만원→원 |
| `ENUM` | 원문 표현을 승인된 표준코드로 매핑 | 양수→`ACQUISITION` |
| `BOOLEAN` | 예·아니오·해당없음을 의미상 구분 | `해당 없음`→`NOT_APPLICABLE` |
| `COMPOSITE` | 반복 표를 배열·구조로 구성 | 특별관계자·지급단계 |
| `CALCULATION` | 공식으로 새 수치를 생성 | 투자금액÷자기자본 |
| `DOCUMENT_LINK` | 다른 접수번호 문서를 확정 관계로 연결 | 결정→완료 |
| `MANUAL_REVIEW` | 자동판정 위험이 높아 C 검토 필요 | 경영권 확보 여부의 모호한 문장 |

### 3.2 정규화 상태

| 상태 | 의미 | 처리 |
|---|---|---|
| `MAPPED` | 승인 규칙으로 표준화 완료 | 계산 입력 후보가 될 수 있음 |
| `UNMAPPED` | 매핑표에 없는 원문 표현 | 원문 보존, 임의 코드 부여 금지 |
| `AMBIGUOUS` | 둘 이상의 표준값으로 해석 가능 | 계산·상태전이 사용 금지 |
| `REVIEW_REQUIRED` | 금융 의미 확인이 필요 | B가 원문·후보코드·근거를 C에게 회신 |
| `NOT_APPLICABLE` | 사건구조상 해당 Fact가 적용되지 않음 | 0·누락과 구분 |
| `MISSING` | 적용되는 Fact지만 원문에 값이 없음 | 추정 금지 |

새로운 원문 표현은 다음 순서로 처리한다.

```text
B가 원문 표현과 후보코드를 수집
→ 임의 확정하지 않고 REVIEW_REQUIRED로 반환
→ C가 금융적 동일성·경계를 검수
→ 승인된 매핑만 정책 버전에 추가
→ 회귀테스트 수행
```

예를 들어 “상호 합의에 의한 거래 백지화”가 기존 매핑에 없으면 raw를 보존하고 `normalizedValue=null`, `normalizationStatus=REVIEW_REQUIRED`, `suggestedValue=TERMINATED` 후보로 회신한다. C 승인 전에는 최신 사건상태를 바꾸지 않는다.

## 4. 원문 근거 최소 조건

핵심 Fact에는 다음 위치정보를 연결한다.

| 필드 | 의미 |
|---|---|
| `receiptNo` | 접수번호 |
| `documentName` | 실제 원문 문서명 |
| `documentRole` | 원공시·정정·결과·해지·첨부 등 역할 |
| `sectionPath` | 장·절·표 경로 |
| `blockType` | `TABLE_CELL/TABLE_ROW/PARAGRAPH/TITLE` 등 |
| `tableIndex/tableName` | 표 식별정보 |
| `rowLabel/columnLabel` | 값의 행·열 머리글 |
| `rawValue/rawUnit` | 실제 원문값과 단위 |
| `sourceText` | 판단에 사용한 원문 문장·표 행 |
| `sourceLocation` | 행·문단·오프셋 등 재현 위치 |
| `noteText` | 각주·산정기준·기타사항 |

숫자 셀만 근거로 저장하지 않는다. 표 머리글, 행 제목, 단위와 산정기준을 함께 보존한다. 정정 Fact는 `beforeEvidence`와 `afterEvidence`, 계산은 모든 입력 Fact의 evidence가 필요하다.

## 5. 결측·비공개·실패 처리

| 상태 | 의미 | 저장·답변 원칙 |
|---|---|---|
| `AVAILABLE` | 원문과 근거가 확인됨 | 값을 반환 가능 |
| `NOT_STATED` | 해당 항목이 원문에 기재되지 않음 | `null`, 추정 금지 |
| `WITHHELD` | 공시유보·비공개가 명시됨 | 유보 사유·기한을 함께 반환 |
| `NOT_APPLICABLE` | 사건 구조상 해당하지 않음 | 0과 구분 |
| `AMBIGUOUS` | 원문은 있으나 의미·단위·대상이 불명확 | 계산 입력 사용 금지 |
| `PARSE_FAILED` | 시스템이 원문을 정상 추출하지 못함 | 데이터 부재가 아니라 시스템 실패로 기록 |

`-`, 공란, `미정`, `해당 없음`, 비공개를 모두 숫자 0이나 문자열 `UNKNOWN`으로 통일하지 않는다.

## 6. 계산 기록 공통 계약

모든 계산은 백엔드의 결정적 로직으로 수행한다.

| 필드 | 의미 |
|---|---|
| `calculationId` | 유형 문서의 계산 ID |
| `inputFactIds` | 사용한 검증 Fact 식별자 |
| `formula` | 실제 공식 |
| `preconditions` | 통화·단위·기간·회계기준·분모 검증 |
| `rawResult` | 충분한 정밀도의 원계산값 |
| `displayResult` | 표시 반올림 적용값 |
| `roundingRule` | 반올림·절사·표시 자릿수 |
| `validationResult` | 공시값과 일치·표시방식 차이·불일치 |
| `policyVersion` | 계산 규칙 버전 |

공시비율이 소수 `d`자리라면 같은 자리로 반올림한 표시값을 우선 비교한다. 원계산값 기준의 이론적 반올림 범위는 `0.5 × 10^-d %p`다. 다만 입력 원문 자체가 반올림·근사값이면 기계적으로 공시 오류라고 단정하지 않는다. 금액 계산에는 이진 부동소수점이 아닌 십진수 연산을 사용한다.

## 7. 사건 상태와 API 답변 상태

사건 상태는 계약·투자·소송 등이 실제 어느 단계인지 나타낸다. API 답변 상태는 질문에 필요한 정보를 얼마나 검증했는지를 나타낸다. 둘을 같은 enum으로 저장하지 않는다.

| API 상태 | 판정 기준 |
|---|---|
| `COMPLETED` | 질문에 필요한 Fact·기준·근거·계산이 모두 검증됨 |
| `PARTIAL` | 확인된 답은 있으나 요청 Fact·조건·후속근거 일부가 누락됨 |
| `UNANSWERABLE` | 대회 제공 데이터에서 핵심 답을 확인할 수 없음 |
| `FAILED` | 파서·검색·DB·계산·서비스 오류로 정상 처리가 불가능함 |

사건이 `IN_PROGRESS`여도 진행상태를 정확히 묻는 질문은 API `COMPLETED`가 될 수 있다.

## 8. 정정·기준시점 조회 모드

| 조회 모드 | 의미 |
|---|---|
| `AS_FILED` | 특정 접수번호가 제출된 당시 값 |
| `LATEST_AS_OF` | 사용자가 지정한 `asOf`까지 확인된 최신 유효값 |
| `FULL_HISTORY` | 최초·정정·후속·완료·해지 전체 이력 |

`asOf`는 공시 Fact가 아니라 질문의 시간상 마감조건이다. `asOf` 이후 제출된 문서는 과거 기준 답변에서 제외한다.

## 9. 골든 후보 필수 구성

승인 전 사례는 `골든 후보`이며 C의 원문 검수가 끝난 뒤에만 고정 골든셋으로 승격한다.

| 필수 항목 | 내용 |
|---|---|
| 질문 ID·질문 | 라우팅할 대표 질문 |
| 대상 문서 | 회사·접수번호·문서 역할 |
| 기대 Fact | raw·단위·normalized·생성 방식·원문 위치 |
| 기대 계산 | 입력값·공식·원계산값·표시값·허용오차 |
| 기대 이력 | 원공시·정정·후속 관계와 `asOf` 상태 |
| 기대 API 상태 | `COMPLETED/PARTIAL/UNANSWERABLE` |
| 허용 답변 요지 | 사실·계산·설명·한계 분리 |
| 치명적 오류 | 단위·대상·상태·근거·해석 오류 목록 |
| 승인 상태 | `C_REVIEW_PENDING/APPROVED/REJECTED` |

원문 표·행·문장 위치가 확인되지 않은 숫자는 골든 후보 기대값으로 참고할 수는 있지만 `APPROVED`로 승격하지 않는다.

## 10. B의 공통 구현·회신 순서

1. 유형별 대상 문서를 Manifest에서 라우팅하고 원문 파일을 연결한다.
2. 문서 구조·표 머리글·행·주석을 보존해 evidence를 생성한다.
3. 유형 문서의 Fact를 `rawValue` 중심으로 추출하고 생성 방식을 기록한다.
4. 원문을 유지한 채 단위·날짜·통화·승인 용어를 정규화한다.
5. 자료형·기간·회계기준·대상·통화 검증 후 `VERIFIED`로 승격한다.
6. 명시 근거가 있는 정정·후속 관계만 확정하고 후보 관계를 자동 병합하지 않는다.
7. 검증된 Fact ID만 계산기에 전달한다.
8. 골든 후보별 구조화 JSON, evidence, 계산 기록, 상태, 불일치를 회신한다.
9. C 승인 후 골든셋으로 고정하고 회귀테스트에 편입한다.
10. 유형 전체 배치에서 누락·미지원·파싱실패·관계미확정 원인을 분리 집계한다.

## 11. C와 B의 승인 경계

| C가 승인할 것 | B가 구현·검증할 것 |
|---|---|
| Fact의 금융적 의미와 비교 가능 조건 | 원문 레이블·섹션을 Fact에 매핑 |
| 금액·통화·VAT·기간·회계기준 정책 | raw/normalized/evidence 저장 |
| 계산식·표현 한계·금지 표현 | 결정적 계산과 사전조건 검증 |
| 골든 기대값·허용 답변·치명적 오류 | 추출값과 기대값의 자동 비교 |
| 해석 가능 범위와 `PARTIAL/UNANSWERABLE` 기준 | 파서·검색·이력·계산 실패 원인 보고 |

C가 파서 구현 방법이나 DB 클래스명을 정할 필요는 없다. B가 금융 의미를 임의로 정하지 않도록 입력·출력 계약과 승인 기준을 명확히 제공하는 것이 이 문서 묶음의 목적이다.
