# 공시 Agent 예선 개발 우선순위 및 3인 역할분담

## 1. 문서 목적

이 문서는 2026 미래에셋증권 AI Festival 공시 Agent 과제의 공식 소개 자료가 공개된 이후, FolioLens 팀의 예선 개발 우선순위와 3인 역할을 다시 정하기 위한 실행계획이다.

기존 FolioLens의 포트폴리오 개인화 아이디어는 유지하되, 예선에서 직접 평가되는 자연어 공시 질의응답 엔진을 먼저 완성하는 것을 목표로 한다.

작성 기준일은 2026년 7월 28일이며, 예선 제출 마감일은 2026년 9월 6일이다.

---

## 2. 공식 과제 기준 핵심 변화

### 2.1 공식 과제의 중심

공식 과제의 중심은 다음과 같다.

> 주최 측이 제공한 공시 데이터에서 자연어 질의에 맞는 정보를 검색하고, 여러 공시를 비교·계산·추론하여 근거와 함께 답변하는 공시 AI Agent

따라서 예선의 핵심 실행 경로는 다음과 같아야 한다.

```text
평가 질의 수신
→ 질의 의도와 조건 분석
→ 관련 기업·기간·공시 검색
→ 필요한 원문과 구조화 데이터 추출
→ 비교·계산·변경 이력 분석
→ HyperCLOVA X를 이용한 답변 생성
→ 참고 공시와 근거를 포함한 JSON 응답
```

### 2.2 반드시 지켜야 하는 데이터 제약

- 주최 측이 제공한 기업과 공시 데이터만 사용한다.
- 대상 기간은 2023년 1월부터 2026년 1분기까지다.
- OpenDART 등 외부 공시 API의 실시간 호출은 평가 경로에서 금지된다.
- 뉴스, 리포트, 위키 등 제공 코퍼스 밖의 데이터를 답변 근거로 사용하지 않는다.
- 공시에서 확인할 수 없는 내용은 추측하지 않고 `확인할 수 없음` 또는 `공시에서 확인되지 않음`으로 답한다.
- 공시에 근거하지 않은 미래 예측과 투자 의견을 생성하지 않는다.
- 서비스 경로에서 사용하는 LLM은 HyperCLOVA X로 제한한다.

### 2.3 기존 FolioLens 기획과의 관계

기존 기획의 다음 요소는 공식 과제와 잘 맞는다.

- 공시 원문 근거 제공
- 정정공시와 원공시 연결
- 공시의 핵심 사실 구조화
- 변화량·증감률·비중을 백엔드가 계산
- 공시에 없는 내용을 추측하지 않는 정책
- HyperCLOVA X와 백엔드 책임 분리
- 평가 API와 웹 API를 어댑터로 분리하는 설계

다음 요소는 예선 핵심 경로에서 우선순위를 낮춘다.

- 회원가입과 로그인 고도화
- 포트폴리오 CRUD
- 보유 비중 기반 중요도 점수
- 투자 가정 등록과 영향 분석
- 포트폴리오 대시보드
- 알림과 주간 리포트
- 뉴스와 공시 불일치 분석

포트폴리오 개인화는 폐기하지 않는다. 공시 질의응답 엔진이 완성된 이후 웹 서비스의 차별화 계층으로 연결한다.

## 3. 개발 전략

### 3.1 하나의 분석 엔진, 두 개의 진입점

```text
                         ┌─ 평가용 GET /answer
공시 질의응답 코어 ──────┤
                         └─ FolioLens 웹 API 및 화면
```

평가 API와 웹 서비스가 서로 다른 분석 로직을 가지면 안 된다. 검색, 계산, 근거 연결, 답변 생성은 하나의 코어 서비스에서 수행하고 입출력 형식만 어댑터에서 변환한다.

### 3.2 우선순위 원칙

모든 작업은 다음 순서로 판단한다.

1. 비공개 평가 질의에 정확히 답할 수 있는가
2. 답변에 필요한 공시를 빠짐없이 검색하는가
3. 수치·비교·계산이 재현 가능한가
4. 모든 핵심 주장에 근거가 연결되는가
5. 정보가 없을 때 안전하게 답변을 거절하는가
6. 평가 서버에서 안정적으로 실행되는가
7. 기술 제안과 웹 시연에서 차별성을 보여주는가

## 4. 팀 역할 개요

실제 이름은 팀 회의에서 아래 역할 A, B, C에 매핑한다.

| 역할 | 주 담당 | 최종 책임 |
|---|---|---|
| 팀원 A | AI 오케스트레이션·평가 API·배포 | 질문부터 최종 답변까지 전체 실행 경로 |
| 팀원 B | 데이터 적재·검색·구조화·계산 | 필요한 공시와 정확한 사실을 코어 엔진에 공급 |
| 팀원 C | 금융 도메인·골든셋·답변 검수·서비스 기획 | 답변 정확성, 근거 완전성, 안전성, 제안 논리 |

역할은 책임을 구분하기 위한 것이며, 특정 담당자만 해당 코드를 이해하는 구조로 만들지 않는다. 모든 핵심 PR은 최소 한 명의 다른 팀원이 검토한다.

## 5. 팀원 A: AI 오케스트레이션·평가 API·배포

### 5.1 핵심 책임

- 평가용 `/answer` API 구현
- 자연어 질문 분석 결과를 검색·계산 모듈로 전달
- 검색 결과와 계산 결과를 HyperCLOVA X 입력으로 구성
- 최종 답변, 검색 근거, 실행 추적을 평가 응답으로 변환
- 타임아웃, 오류 처리, 요청 추적, 배포 안정성 확보
- Docker 기반 재현 환경과 README 관리

### 5.2 구현 대상

#### 평가 API 어댑터

초기 계약은 공식 자료의 예시 스키마를 기준으로 구현한다.

```http
GET /answer?question_id={id}&question={질문}
```

```json
{
  "question_id": "Q-001",
  "question": "평가 질의 원문",
  "retrieved_context": "답변 생성에 사용한 검색 문서",
  "think_trace": "검색·비교·계산·도구 사용 과정의 요약",
  "answer": "최종 답변"
}
```

`think_trace`에는 모델의 원시 내부 사고과정을 그대로 노출하지 않는다. 다음과 같은 재현 가능한 실행 요약을 기록한다.

- 해석한 기업·기간·공시 유형·지표
- 검색한 문서와 선택 이유
- 적용한 비교 기준
- 수행한 계산식과 입력값
- 답변 제한 또는 확인 불가 사유

#### 질문 계획 모델

질문을 다음 공통 구조로 변환한다.

```json
{
  "questionType": "MULTI_COMPANY_COMPARISON",
  "companies": ["기업 A", "기업 B"],
  "period": {
    "from": "2025-01-01",
    "to": "2025-12-31"
  },
  "disclosureTypes": ["FACILITY_INVESTMENT"],
  "metrics": ["investmentAmount"],
  "operations": ["COMPARE", "RANK"],
  "accountingBasis": null,
  "needsClarification": false
}
```

#### 답변 조립

HyperCLOVA X에는 다음 정보만 제공한다.

- 사용자 질문
- 검색된 공시 원문 구간
- 구조화된 사실
- 백엔드가 계산한 결과
- 근거 식별자
- 허용 표현과 금지 표현

HyperCLOVA X가 금액, 증감률, 순위 등을 새로 계산하게 하지 않는다.

#### 장애 처리

- 질문 누락: `400`
- 지원할 수 없는 질문: 확인 가능한 범위와 한계 반환
- 검색 결과 없음: `공시에서 확인되지 않음`
- 모델 호출 실패: 제한된 재시도 후 명시적 오류
- 전체 요청 시간 초과: 부분 결과 또는 표준 오류
- 동일 `question_id` 재요청: 중복 처리 정책 적용

## 6. 팀원 B: 데이터 적재·검색·구조화·계산

### 6.1 핵심 책임

- 주최 측 제공 데이터의 형식과 품질 분석
- 기업 마스터, 공시 메타데이터, 공시 원문 적재
- 검색용 문서 분할, 색인, 필터 설계
- 질문 조건에 맞는 후보 공시 검색
- 정기·수시·지분공시의 핵심 사실 구조화
- 기업·연도·공시 간 비교 및 계산 함수 구현
- 원공시·정정·해지·후속공시 관계 연결

### 6.2 현재 구현에서 유지할 부분

- `Company` 엔티티
- `CompanyRepository`
- 기업명·종목코드 검색
- PostgreSQL과 Flyway
- 공시 사실, 근거, 문서 관계를 분리하는 데이터 모델
- 백엔드 결정적 계산 원칙

### 6.3 현재 구현에서 중단하거나 전환할 부분

OpenDART ZIP 다운로드·파싱 코드는 학습 및 개발 도구로 보존할 수 있지만, 평가 실행 경로에서는 사용하지 않는다.

```text
평가 프로필
OPENDART_ENABLED=false
```

기업 동기화 구현의 다음 단계는 OpenDART DB 저장이 아니라 주최 측 기업 마스터 어댑터를 만드는 것이다.

```text
CompanyDataProvider
├─ CompetitionDatasetCompanyDataProvider  ← 예선 우선
└─ OpenDartCompanyDataProvider             ← 평가 경로 비활성
```

### 6.4 데이터 적재 파이프라인

```text
제공 파일 수신
→ 파일 해시와 버전 기록
→ 기업 마스터 적재
→ 공시 메타데이터 적재
→ 공시 원문 저장
→ 문서 섹션·청크 분리
→ 검색 인덱스 생성
→ 핵심 사실 추출
→ 공시 관계 연결
→ 적재 검증 리포트 생성
```

적재 검증 리포트에는 최소한 다음을 포함한다.

- 전체 기업 수
- 전체 공시 수
- 공시 유형별 문서 수
- 연도별 문서 수
- 원문 누락 수
- 기업 매핑 실패 수
- 중복 문서 수
- 파싱 실패 수
- 정정·후속 관계 연결 수

### 6.5 검색 전략

처음부터 복잡한 GraphRAG를 구현하지 않는다. 다음 순서로 성능을 올린다.

1. 기업, 기간, 공시 유형 메타데이터 필터
2. 제목과 본문 키워드 검색
3. 문서 섹션 단위 검색
4. 임베딩 검색
5. 키워드와 임베딩 결과 결합
6. 필요할 때 Re-ranker 적용

임베딩 모델과 네이버클라우드 서비스 사용 가능 범위는 8월 6일 설명회에서 확인한다.

### 6.6 계산 함수 우선순위

다음 계산은 LLM이 아닌 Java 코드로 구현한다.

1. 절대 증감액
2. 증감률
3. 구성 비중
4. 기업 간 크기 비교
5. 연도별 추세
6. 계약 체결 후 해지 여부
7. 공시 정정 전후 변경량
8. 자금조달 유형별 합계

각 계산 결과에는 다음을 함께 반환한다.

- 사용한 입력값
- 단위와 통화
- 대상 기간
- 연결·별도 기준
- 계산식
- 계산 불가 사유
- 근거 공시 식별자

## 7. 팀원 C: 금융 도메인·골든셋·답변 검수·서비스 기획

### 7.1 핵심 책임

- 평가 질의 유형 정의
- 기업·회계·공시 용어 사전 작성
- 골든 질문과 정답·근거 구축
- 연결·별도, 기간, 단위, 통화 기준 검수
- 답변의 금융 표현과 안전성 검수
- 확인 불가 및 역질문 정책 정의
- 기술 제안서와 웹 서비스 차별화 시나리오 작성

### 7.2 골든셋 구성

최소 40개 질문을 작성하고 다음 유형을 고르게 포함한다.

| 유형 | 최소 개수 | 예시 |
|---|---:|---|
| 단일 사실 조회 | 8 | 특정 연도 연결 매출액 |
| 공시 요약 | 6 | 분기보고서의 주요 투자 계획 |
| 기업 간 비교 | 6 | 두 기업의 설비투자 규모 비교 |
| 연도 간 비교 | 6 | 2023년과 2025년 핵심 사업 변화 |
| 계산 질의 | 5 | 증감률, 구성 비중, 유형별 합계 |
| 변경 이력 | 4 | 정정 전후 금액 변화 |
| 복합 문서 추론 | 3 | 계약 이후 해지 공시 존재 여부 |
| 확인 불가·공격 대응 | 2 | 코퍼스 밖 뉴스 질문, 투자 추천 요청 |

각 골든 질문은 다음 형식으로 관리한다.

```json
{
  "questionId": "GOLD-001",
  "question": "질문",
  "questionType": "SINGLE_FACT",
  "expectedCompanies": ["기업명"],
  "expectedDisclosureIds": ["공시 식별자"],
  "expectedFacts": [
    {
      "name": "revenue",
      "value": "값",
      "unit": "KRW",
      "period": "2025",
      "accountingBasis": "CONSOLIDATED"
    }
  ],
  "requiredEvidence": ["근거 구간"],
  "allowedAnswer": "허용 가능한 답변 요지",
  "forbiddenClaims": ["근거 없는 주장"],
  "shouldRefuse": false
}
```

### 7.3 답변 검수 기준

각 답변을 다음 항목으로 0~2점 평가한다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 사실 정확성 | 핵심 오류 | 일부 불명확 | 정확 |
| 검색 근거 완전성 | 핵심 근거 없음 | 일부 근거만 있음 | 필수 근거 포함 |
| 요구사항 충족 | 주요 항목 누락 | 일부 누락 | 모두 충족 |
| 비교·계산 정확성 | 계산 오류 | 설명 부족 | 입력·식·결과 정확 |
| 근거 기반 | 환각 포함 | 표현이 과도함 | 근거 범위 내 답변 |
| 정보 한계 대응 | 무리한 답변 | 모호한 제한 | 명확한 거절·역질문 |
| 표현 안전성 | 투자 권유 | 단정적 표현 | 조건부·중립적 표현 |

핵심 골든셋은 총점뿐 아니라 다음 치명 오류가 0건이어야 한다.

- 다른 기업의 수치를 답변
- 연결과 별도 수치를 혼합
- 다른 기간의 수치를 비교
- 단위를 잘못 변환
- 원공시와 정정공시를 반대로 해석
- 공시에 없는 사실 생성
- 투자 추천 또는 미래 가격 예측

### 7.4 서비스 차별화 기획

평가 엔진이 안정된 후 FolioLens 차별화 기능을 다음 순서로 정리한다.

## 15. 기능 완료 정의

하나의 기능은 다음 조건을 모두 만족해야 완료로 처리한다.

1. 입력과 출력 계약이 문서화됐다.
2. 정상 시나리오 테스트가 있다.
3. 오류 또는 확인 불가 시나리오 테스트가 있다.
4. 공시 근거가 연결된다.
5. 수치가 있다면 단위·기간·회계 기준이 명확하다.
6. LLM이 아닌 백엔드가 필요한 계산을 수행한다.
7. 팀원 C가 금융 의미와 표현을 검수했다.
8. Docker 환경에서 재현된다.
9. 로그에 인증정보나 전체 민감 입력이 노출되지 않는다.
10. 기존 골든셋 결과를 악화시키지 않는다.

## 18. 최종 방향

FolioLens의 최종 구조는 다음 두 층으로 정의한다.

### 기본 층: 예선 평가 핵심

> 제공된 공시 데이터에서 질문에 필요한 문서를 정확히 찾고, 여러 문서를 비교·계산하여 근거와 함께 답변하는 공시 질의응답 Agent

### 차별화 층: FolioLens 서비스

> 동일한 공시 질의응답 엔진을 사용자의 포트폴리오와 투자 가정에 연결해, 개인에게 중요한 변화와 확인 지표를 우선적으로 보여주는 서비스

기본 층이 완성되지 않은 상태에서 차별화 층을 확장하지 않는다. 예선 개발의 최우선 목표는 비공개 질문에 정확하고 근거 있는 답변을 안정적으로 반환하는 것이다.
