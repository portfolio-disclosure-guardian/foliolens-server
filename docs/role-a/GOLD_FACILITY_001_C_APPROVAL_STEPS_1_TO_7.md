# GOLD-FACILITY-001 금융 도메인 승인 명세

## 0. 문서 목적과 작업의 명칭

이 문서는 역할 C가 SK하이닉스 신규시설투자 대표 질문 1건에 대해 수행한 1~7단계 검토 결과를 역할 A와 역할 B에게 전달하기 위한 금융 도메인 승인 명세다.

이 작업은 다음과 같이 명명한다.

> **금융 도메인 골든 케이스 승인 명세 작성**

조금 더 구체적으로는 다음 작업을 한 것이다.

> 대회 제공 공시 원문에서 질문에 필요한 정보를 확인하고, 그 정보를 어떤 Fact로 취급할지, 어떻게 정규화·계산·판정·표현할지를 결정하여 백엔드 구현과 답변 검증의 기준을 만든 작업

이 작업이 필요한 이유는 다음과 같다.

1. 역할 A가 자연어 질문을 검색·조회·계산·답변 단계로 안정적으로 나눌 수 있게 한다.
2. 역할 B가 공시 원문의 어느 값을 어떤 의미로 추출하고 저장해야 하는지 알 수 있게 한다.
3. 계산을 LLM이 임의로 수행하지 않고 백엔드의 결정적 로직으로 실행하게 한다.
4. B의 자동추출 결과를 비교할 수 있는 정답 기준, 즉 골든 케이스를 제공한다.
5. 공시 사실, 백엔드 계산, 금융적 해석을 구분하여 근거 없는 단정과 투자 권유를 방지한다.

이 문서는 백엔드 구현 완료 문서가 아니다. `facility.*` Fact ID는 C가 의미를 승인하는 논리 계약이며, 역할 B가 실제 저장·추출·조회·계산 구조로 구현해야 한다.

# 2단계. Fact 후보와 필수도 결정

## 2.1 핵심 원칙

질문 문장은 무한히 달라질 수 있지만, 공시에서 추출해야 하는 의미 단위와 승인된 계산은 유한하게 관리한다. 사용자의 문장마다 새로운 Fact나 계산식을 만들지 않는다.

이번 수직 슬라이스에서는 기존 프로젝트 명세와 테스트에서 사용 중인 `facility.*` namespace를 유지한다. 별도의 `investment.*` 중복 namespace를 추가하지 않는다.

## 2.2 핵심 Fact 후보

| Fact ID | 금융적 의미 | 원문 레이블 | 필수도 | 질문에서의 역할 |
|---|---|---|---|---|
| `facility.target` | 투자 대상 설비·사업 | 투자대상 | `SUPPORTING` | 대상 식별 보강 |
| `facility.amount` | 회사가 공시한 계획 투자금액 | 투자금액(원) | `REQUIRED` | 직접 답변 및 계산 분자 |
| `facility.equity_amount` | 공시 비율 계산에 사용된 자기자본 | 자기자본(원) | `REQUIRED` | 계산 분모 |
| `facility.equity_ratio` | 회사가 공시에 직접 기재한 자기자본 대비 비율 | 자기자본대비(%) | `REQUIRED` | 재계산값과 비교할 공시값 |
| `facility.purpose` | 회사가 공시한 투자목적 | 투자목적 | `REQUIRED` | 직접 답변 |
| `facility.start_date` | 공시상 투자기간 시작일 | 시작일 | `SUPPORTING` | 일정 의미 보강 |
| `facility.end_date` | 공시상 투자기간 종료 예정일 | 종료일 | `SUPPORTING` | 일정 의미 보강 |
| `facility.decision_date` | 이사회가 투자를 결정한 날짜 | 이사회결의일(결정일) | `SUPPORTING` | 기준시점 식별 |

대상 회사명, 접수번호, 공시일, 공시 유형은 위 8개 Fact와 별개의 문서 식별 메타데이터로 반드시 보존한다.

## 2.3 `facility.equity_ratio`의 의미

`facility.equity_ratio`는 백엔드가 새로 계산한 값이 아니라 공시 원문에 직접 기재된 비율이다.

```text
facility.equity_ratio
= 공시 직접값 9.90%

FACILITY_EQUITY_RATIO_CHECK
= 투자금액과 자기자본을 사용한 별도 계산 및 검증 결과
```

공시값과 재계산값을 하나의 값으로 덮어쓰거나 혼합하면 안 된다.

## 2.4 최소 Evidence 조건

각 핵심 Fact를 인정하려면 최소한 다음 정보가 있어야 한다.

- `sourceProvider = CONTEST`
- 문서 식별자와 접수번호
- 데이터셋 상대 파일 경로
- section·table·row 또는 동등한 원문 위치
- 원문 레이블
- 원문값
- 원문 단위
- 해당 값의 의미를 제한하는 주석
- 정정·후속공시가 있으면 기준시점과 연결관계

모델이 만든 요약문이나 외부 DART 화면은 이 골든 케이스의 원문 Evidence로 인정하지 않는다.

## 3.3 의미를 제한하는 원문 주석

표의 `7. 기타 투자판단과 관련한 중요사항`에서 다음 내용을 직접 확인했다.

1. 자기자본은 최근 사업연도 말 연결재무제표 기준이다.
2. 투자금액과 투자기간은 투자 진행과정 및 경영환경 변화 등에 따라 변동될 수 있다.
3. 투자기간의 시작일은 이사회 결의일이다.
4. 투자기간의 종료일은 예정일이며 향후 추진 과정에서 변동될 수 있다.

따라서 다음과 같이 해석한다.

| 공시 내 정보 | 올바른 의미 | 금지되는 오해 |
|---|---|---|
| 투자금액 | 공시된 계획 투자금액 | 이미 집행을 완료한 금액 |
| 자기자본 | 최근 사업연도 말 연결 기준 자기자본 | 공시일 현재 별도 자기자본 |
| 시작일 | 이사회 결의일을 시작일로 기재 | 실제 착공일 확정 |
| 종료일 | 계획상 종료 예정일 | 확정 준공일 |

3단계의 결과는 B가 추출한 Fact가 아니라, 향후 Fact 정의와 자동추출 결과를 검증할 **공시 원문 기준정보**다.

# 4단계. 원문값 정규화와 비교 가능 조건

## 4.1 정규화 원칙

원문값과 정규화값을 모두 보존한다. `.raw`, `.value`, `.normalized_value`는 별개의 금융 Fact를 늘리는 표현이 아니라 하나의 Fact envelope 안에서 원문과 정규화 표현을 구분하는 속성이다.

권장 논리 구조는 다음과 같다.

```text
factId
rawLabel
rawValue
rawUnit
normalizedValue
normalizedUnit
normalizationMethod
qualifiers
evidence
```

실제 클래스·DB 필드명은 역할 B가 결정하되, 의미와 추적 가능성을 손상하면 안 된다.

## 4.2 핵심 정보 정규화

| Fact ID | 원문값 | 정규화값 | 단위·형식 | 생성 방식 |
|---|---|---:|---|---|
| `facility.target` | 청주 M15X 건설 | 청주 M15X 건설 | 문자열 | `DIRECT_RAW` |
| `facility.amount` | `5,296,200,000,000` | `5296200000000` | `KRW` | `DIRECT_NORMALIZED` |
| `facility.equity_amount` | `53,503,752,397,611` | `53503752397611` | `KRW` | `DIRECT_NORMALIZED` |
| `facility.equity_ratio` | `9.90` | `9.90` | `%` | `DIRECT_NORMALIZED` |
| `facility.purpose` | 선제적인 반도체 수요 대응을 위한 차세대 DRAM 생산능력 확장 | 원문 동일 | 문자열 | `DIRECT_RAW` |
| `facility.start_date` | `2024-04-24` | `2024-04-24` | ISO 날짜 | `DIRECT_NORMALIZED` |
| `facility.end_date` | `2026-10-30` | `2026-10-30` | ISO 날짜 | `DIRECT_NORMALIZED` |
| `facility.decision_date` | `2024-04-24` | `2024-04-24` | ISO 날짜 | `DIRECT_NORMALIZED` |

`DIRECT_NORMALIZED`는 새로운 경제적 값을 계산했다는 뜻이 아니다. 공시에 직접 기재된 값을 손실 없이 숫자·날짜·통화 형식으로 바꿨다는 뜻이다.

## 4.3 금액 정책

```text
facility.amount.rawValue = "5,296,200,000,000"
facility.amount.rawUnit = "원"
facility.amount.normalizedValue = 5296200000000
facility.amount.normalizedUnit = "KRW"
```

- 조·억 원으로 축약한 표시값을 계산 입력으로 사용하지 않는다.
- VAT 포함·별도 여부는 원문에 없으므로 `UNKNOWN`이다.
- VAT를 임의로 가감하지 않는다.
- 투자금액은 계획금액이며 실제 집행 완료액으로 바꾸지 않는다.
- 계산에는 정밀도 손실이 없는 정규화값을 사용한다.

## 4.4 자기자본의 연결·별도 기준

이번 원문은 자기자본이 최근 사업연도 말 연결재무제표 기준임을 직접 밝힌다.

```text
accounting_scope = CONSOLIDATED
reference_period_type = LATEST_FISCAL_YEAR_END
reference_date = UNKNOWN
```

연결재무제표는 SK하이닉스 지배기업과 종속회사를 하나의 경제적 실체로 보고 작성한 재무제표다. 별도재무제표는 SK하이닉스 법인 자체만을 대상으로 한다.

이번 비율 검증은 공시가 사용한 연결 자기자본을 그대로 사용해야 한다. 별도 자기자본이나 현재 시점의 최신 자기자본으로 교체하면 공시된 `9.90%`의 검증이 아니게 된다.

다른 문서에 대한 원칙은 다음과 같다.

| 원문 기재 | 분류 |
|---|---|
| 연결재무제표 기준 명시 | `CONSOLIDATED` |
| 별도·개별재무제표 기준 명시 | `SEPARATE` |
| 기준 설명 없음 | `UNKNOWN` |

회사가 종속회사를 보유한다는 이유만으로 연결 기준을 추정하지 않는다. 기준이 없으면 숫자로 같은 공시의 비율을 계산할 수 있더라도 연결·별도 여부는 `UNKNOWN`이라고 밝혀야 한다.

## 4.5 날짜 의미

| Fact ID | 값 | 의미 속성 |
|---|---|---|
| `facility.start_date` | 2024-04-24 | `BOARD_RESOLUTION_DATE` 기준 시작일 |
| `facility.end_date` | 2026-10-30 | `SCHEDULED_END_DATE`, `PLANNED` |
| `facility.decision_date` | 2024-04-24 | 이사회결의일 |

시작일과 결정일은 값이 같지만 의미가 다르므로 합치지 않는다. 종료일은 확정 완료일이 아니라 예정일로 표현한다.

## 4.6 이번 계산의 비교 가능 조건

| 조건 | 확인 결과 | 판정 |
|---|---|---|
| 동일 공시에서 가져온 값 | 접수번호 `20240424800596` | 충족 |
| 동일 통화 | 투자금액·자기자본 모두 원화 | 충족 |
| 동일 단위 | 모두 원 단위 | 충족 |
| 분모 존재 | 자기자본 존재 | 충족 |
| 분모가 양수 | `53,503,752,397,611 > 0` | 충족 |
| 회계범위 확인 | 최근 사업연도 말 연결 기준 | 충족 |
| 양쪽 원문 근거 확인 | 표 3행·4행 | 충족 |

이번 투자금액과 자기자본은 공시 비율 검증에 사용할 수 있다.

## 4.7 비교 불가·계산 불가 조건

- 투자금액 또는 자기자본 누락
- 통화·단위 불명확
- 자기자본이 0
- 자기자본이 음수여서 일반적인 상대 규모 해석이 부적절
- 숫자가 `-`, `미정`, `추후 확정`으로만 기재
- 원문 파손으로 숫자 파싱 불가
- 서로 다른 정정 버전의 값 혼합
- 공시 당시 자기자본을 현재 자기자본으로 임의 교체

누락값을 0으로 대체하지 않는다.

# 5단계. 계산·반올림·허용 오차 정책

## 5.1 계산 ID와 공식

```text
계산 ID: FACILITY_EQUITY_RATIO_CHECK

자기자본 대비 투자비율(%)
= facility.amount ÷ facility.equity_amount × 100
```

## 5.2 입력값

| 역할 | 값 |
|---|---:|
| 분자 | `5296200000000 KRW` |
| 분모 | `53503752397611 KRW` |
| 비교할 공시값 | `9.90%` |

## 5.3 재계산 결과

```text
5,296,200,000,000
÷ 53,503,752,397,611
× 100
= 9.898744971458265453112664230...%
```

계산 중간에는 반올림하지 않는다. 계산에는 원 단위의 손실 없는 값을 사용하고, 이진 부동소수점 때문에 금액이나 비율이 변하지 않도록 충분한 십진 정밀도를 보장한다.

## 5.4 표시 자릿수와 반올림

공시 원문은 `9.90`으로 소수 둘째 자리까지 표시했다. 따라서 검증 비교값도 소수 둘째 자리로 맞춘다.

```text
원계산값: 9.898744971458265...%
반올림 방식: HALF_UP
비교 표시값: 9.90%
```

`HALF_UP`은 일반적인 사사오입이다. 이는 현재 골든 케이스를 위한 C의 결정적 내부 정책이며, 다른 공시 원문이 별도 절사·반올림 방식을 명시하면 원문의 명시 규칙을 우선한다.

## 5.5 허용 오차

공시 비율의 소수 자릿수를 `d`라고 하면 마지막 표시단위의 절반은 다음과 같다.

```text
반올림 범위 참고값 = 0.5 × 10^-d %p
```

이번 공시는 `d = 2`이므로 반올림 범위 참고값은 `0.005%p`다. `%p`는 두 백분율 값 사이의 차이를 나타내는 퍼센트포인트다.

```text
공시값과 원계산값의 차이
= |9.90 - 9.898744971458265...|
= 0.0012550285417345...%p
```

일치 판정은 단순히 고정 `0.01%p` 허용치를 적용하지 않는다. 다음 규칙을 우선한다.

```text
round(재계산 원값, 공시 표시 자릿수, HALF_UP)
== 공시 비율
```

정확히 반올림 경계에 걸리는 값은 `HALF_UP` 결과로 판정하며, 반 단위를 무조건 포함하는 단순 `<=` 비교만 사용하지 않는다.

## 5.6 계산 판정

| 판정 | 의미 |
|---|---|
| `MATCH` | 동일 표시 자릿수로 반올림한 재계산값과 공시값이 같음 |
| `MISMATCH` | 반올림 후에도 공시값과 다름 |
| `NOT_CALCULABLE` | 입력 누락, 분모 0, 단위 불명확 등으로 계산 불가 |
| `NOT_COMPARABLE` | 산술은 가능하나 음수 자기자본·기준 혼합 등으로 정상 비교 부적합 |
| `APPROXIMATE` | 입력 자체가 `약`, 반올림 금액 등이라 근사 검증만 가능 |

이번 판정은 다음과 같다.

```text
계산 판정 = MATCH
```

`MISMATCH`가 나와도 곧바로 허위공시나 회사 오류로 단정하지 않는다. 동일 공시에 기재된 값으로 재계산했을 때 반올림 범위를 넘어 일치하지 않는다고만 말하고, 정정공시·계산 기준·추출값을 추가 확인한다.

## 5.7 무수히 많은 질문과 계산식 처리 원칙

질문마다 새로운 계산식을 만들지 않는다.

```text
자연어 질문
→ 질문 의도 분류
→ 필요한 Fact 선택
→ 승인된 계산 ID 선택
→ 입력조건 검증
→ 백엔드 결정적 계산
→ 근거와 한계를 포함한 답변
```

예를 들어 아래 질문은 표현이 다르지만 모두 `FACILITY_EQUITY_RATIO_CHECK`를 사용한다.

- 자기자본에 비해 투자 규모가 얼마나 되는가?
- 투자금액은 자본의 몇 퍼센트인가?
- 공시된 자기자본 대비 비율이 맞는가?

기존 승인 계산으로 답할 수 없는 질문에 대해 LLM이 새 산식을 즉석에서 만들면 안 된다. 필요한 Fact와 승인 정책이 없으면 `판단 불가` 또는 `UNANSWERABLE`로 처리하고, 반복되는 요구가 확인될 때 C가 새 계산 후보를 검토한다.

# 6단계. 답변 상태와 Claim별 Evidence 정책

## 6.1 답변 상태와 계산 판정은 별개

```text
답변 상태: 질문에 충분히 답했는가?
계산 판정: 공시 비율과 재계산값이 일치하는가?
```

공시 비율이 불일치하더라도 필요한 정보와 근거로 불일치를 완전히 설명했다면 답변 상태는 `COMPLETED`다.

## 6.2 답변 상태

| 상태 | 의미 |
|---|---|
| `COMPLETED` | 질문의 모든 필수 내용을 대회 원문 근거와 계산으로 답함 |
| `PARTIAL` | 질문의 일부는 답하지만 하나 이상의 필수 항목이나 검증이 누락 |
| `UNANSWERABLE` | 정상 검색·검증 후에도 대회 데이터로 핵심을 답할 수 없음 |
| `FAILED` | DB·파일·파서·검색·계산 모듈 등 시스템 실행 실패 |

`FAILED`는 금융적 답변 충족도가 아니라 역할 A·B의 실행 상태다.

## 6.3 `COMPLETED` 조건

다음을 모두 충족해야 한다.

1. 대상 공시를 정확한 접수번호로 찾는다.
2. 투자금액과 원문 근거가 있다.
3. 투자목적과 원문 근거가 있다.
4. 자기자본과 원문 근거가 있다.
5. 공시 비율과 원문 근거가 있다.
6. 단위와 자기자본 회계범위를 확인한다.
7. 승인 공식으로 비율을 재계산한다.
8. 반올림 규칙으로 `MATCH` 또는 `MISMATCH`를 판정한다.
9. 사실·계산·판정 Claim을 각각 근거에 연결한다.

이번 골든 케이스는 다음 상태다.

```text
답변 상태 = COMPLETED
계산 판정 = MATCH
```

## 6.4 `PARTIAL` 예시

| 확인 상황 | 판정과 표현 |
|---|---|
| 투자금액·목적은 있으나 자기자본 없음 | `PARTIAL`; 비율 재계산 불가 명시 |
| 투자금액·자기자본은 있으나 공시 비율 없음 | `PARTIAL`; 계산값은 제시 가능하나 공시값 검증 불가 |
| 투자금액·비율은 있으나 목적 없음 | `PARTIAL`; 목적 확인 불가 명시 |
| 값은 있으나 핵심 원문 위치가 없음 | 검증된 Fact로 인정하지 않고 `PARTIAL` 또는 실행 장애이면 `FAILED` |
| 단위 불명확 | `PARTIAL`; 비율 계산 보류 |

## 6.5 `UNANSWERABLE`과 `FAILED` 구분

```text
정상 검색 후 대회 데이터에 답이 없음
→ UNANSWERABLE

원문은 존재하지만 파일·파서·DB 오류로 확인하지 못함
→ FAILED
```

현재 주가, 목표주가, 미래 수익률처럼 대회 공시에 없는 정보는 외부 검색 없이 `UNANSWERABLE`로 처리한다.

## 6.6 Claim별 근거

| Claim ID | 답변 주장 | 유형 | 최소 근거 |
|---|---|---|---|
| `CLAIM-01` | 투자금액은 5조 2,962억 원 | `FACT` | 투자금액 표 행과 원 단위 값 |
| `CLAIM-02` | 투자목적은 차세대 DRAM 생산능력 확장 | `FACT` | 투자목적 표 행 |
| `CLAIM-03` | 자기자본은 53,503,752,397,611원 | `FACT` | 자기자본 표 행 |
| `CLAIM-04` | 공시 비율은 9.90% | `FACT` | 자기자본대비 표 행 |
| `CLAIM-05` | 자기자본은 최근 사업연도 말 연결 기준 | `FACT` | 기타 투자판단사항 원문 |
| `CLAIM-06` | 재계산값은 약 9.8987% | `CALCULATION` | 공식, 두 입력값, 각 입력 Evidence, 계산 기록 |
| `CLAIM-07` | 소수 둘째 자리 반올림 시 9.90%로 일치 | `INTERPRETATION` | 공시값, 계산값, 자릿수, 반올림 정책, `MATCH` 판정 |

### 유형별 근거 원칙

- `FACT`: 검증된 공시 정보와 해당 원문 Evidence가 필요하다.
- `CALCULATION`: 공식, 모든 입력 Fact, 각 입력의 Evidence, 원계산값과 표시값이 필요하다.
- `INTERPRETATION`: 사용한 Fact·계산·판정 정책과 불확실성 또는 한계 표현이 필요하다.
- 한 Evidence가 여러 Fact를 뒷받침할 수 있지만 연결 관계는 각각 명시한다.
- 모델이 만든 요약문은 원문 Evidence로 인정하지 않는다.
- 답변에 사용하지 않은 Evidence를 핵심 근거처럼 표시하지 않는다.

# 7단계. 허용·금지 표현과 골든 답변

## 7.1 답변 작성 순서

```text
1. 공시 사실
2. 백엔드 계산
3. 제한된 판정·해석
4. 필요한 주의사항
```

## 7.2 허용 표현

| 상황 | 허용 표현 |
|---|---|
| 출처 한정 | `대회 제공 공시 원문에 따르면` |
| 공시 정보 | `공시된 투자금액은 ...입니다.` |
| 계산 | `공시에 기재된 금액으로 재계산하면 ...입니다.` |
| 일치 | `공시와 동일한 자릿수로 반올림하면 ...로 일치합니다.` |
| 불일치 | `허용되는 반올림 범위를 넘어 일치하지 않습니다.` |
| 근거 부족 | `대회 제공 공시 원문에서 해당 항목을 확인할 수 없습니다.` |
| 일정 | `공시된 종료 예정일은 ...입니다.` |

## 7.3 금지 표현

### 투자 권유·가격 예측

- 매수·매도 권유
- 목표주가 제시
- 주가 상승·하락 확정
- 수익 보장 또는 성공확률 단정

### 근거 없는 재무판단

- 투자금액이 크므로 유동성 위기가 발생한다는 단정
- 회사가 투자를 충분히 감당할 수 있다는 단정
- 투자수익성과 사업 성공 여부 단정

### 계획과 실적의 혼동

- 계획 투자금액을 이미 지출한 금액으로 표현
- 종료 예정일을 확정 준공일로 표현
- 시설증설 결정만으로 실제 생산능력 확대 완료를 단정

### 불일치의 과도한 해석

- `회사가 비율을 허위로 공시했다.`
- `공시가 조작됐다.`
- 추가 확인 없이 회사의 고의나 오류를 확정

## 7.4 근거 부족 시 문구

### 자기자본 누락

> 투자금액과 투자목적은 확인되지만, 자기자본이 확인되지 않아 자기자본 대비 비율을 재계산할 수 없습니다.

### 공시 비율 누락

> 투자금액과 자기자본으로 비율을 계산할 수는 있지만, 원문에 비교할 공시 비율이 없어 기재 비율의 정확성은 판단할 수 없습니다.

### 단위 불명확

> 금액의 단위를 확인할 수 없어 비율 계산에 사용할 수 없습니다.

### 공시 미발견

> 대회 제공 데이터에서 해당 조건에 맞는 공시를 확인할 수 없어 답변할 수 없습니다.

## 7.5 비율 불일치 시 문구

> 공시 기재 비율은 X%이지만, 동일 공시에 기재된 투자금액과 자기자본으로 재계산한 값은 Y%입니다. 두 값은 공시 표시 자릿수에 따른 반올림 범위를 넘어 일치하지 않습니다. 정정공시, 계산 기준 및 원문 추출값을 추가로 확인할 필요가 있습니다.

이 경우에도 질문에 필요한 모든 항목과 근거를 제시했다면 답변 상태는 `COMPLETED`, 계산 판정은 `MISMATCH`다.

## 7.6 이번 골든 답변

> 대회 제공 공시 원문에 따르면, SK하이닉스가 2024년 4월 결정한 청주 M15X 건설의 투자금액은 5조 2,962억 원이며, 투자목적은 선제적인 반도체 수요 대응을 위한 차세대 DRAM 생산능력 확장입니다. 공시에 기재된 최근 사업연도 말 연결 자기자본 53조 5,037억 5,239만 7,611원을 기준으로 `투자금액 ÷ 자기자본 × 100`을 계산하면 약 9.8987%입니다. 이를 공시와 동일하게 소수 둘째 자리로 반올림하면 9.90%이므로 공시된 자기자본 대비 비율과 일치합니다. 다만 공시 원문은 투자금액과 투자기간이 진행 과정 및 경영환경에 따라 변경될 수 있다고 밝히고 있습니다.

## 7.7 골든 답변의 기대 상태

```text
answerStatus = COMPLETED
calculationStatus = MATCH
evidenceStatus = VERIFIED
sourceProvider = CONTEST
```

## 8. A와 B가 이 문서를 사용하는 방법

이 절은 8단계 최종 패키지를 확정하기 전, 1~7단계 결과를 구현에 연결하기 위한 안내다.

### 8.1 역할 B의 순차 작업

1. 대회 manifest에서 접수번호 `20240424800596` 문서를 조회한다.
2. 확장자가 아니라 실제 HTML 구조를 기준으로 `table#XFormD1_Form0_Table0`을 파싱한다.
3. 표 레이블과 행 구조로 핵심 8개 정보를 추출한다.
4. 원문 레이블·값·단위·표 위치를 Evidence로 보존한다.
5. C가 승인한 의미대로 `facility.*` Fact 구조를 구현한다.
6. 원문값과 정규화값을 같은 Fact envelope에서 함께 보존한다.
7. 자기자본의 연결 기준, 시작일 기준, 종료일 예정 성격을 주석 Evidence와 연결한다.
8. `FACILITY_EQUITY_RATIO_CHECK`를 결정적 계산으로 구현한다.
9. 공시 비율과 재계산 결과를 별도로 보존하고 `MATCH`를 반환한다.
10. 실제 추출 결과를 이 문서의 원문 기준정보와 비교하는 테스트를 작성한다.

역할 B가 임의로 하면 안 되는 일:

- `facility.equity_ratio`에 재계산값을 덮어쓰기
- 원문에 없는 VAT 상태나 정확한 자기자본 기준일 추정
- 현재 환율·현재 자기자본 등 외부 값을 사용
- 누락값을 0으로 대체
- LLM에게 숫자 계산을 위임

### 8.2 역할 A의 순차 작업

1. 대표 질문에서 회사·기간·공시 유형·접수번호 조건을 구성한다.
2. 검색 결과에서 접수번호 `20240424800596`을 선택한다.
3. 직접 답변용 Fact와 계산 입력 Fact를 구분한다.
4. 비율 검증 질문에만 `FACILITY_EQUITY_RATIO_CHECK` 단계를 포함한다.
5. B가 반환한 Fact·Evidence·계산 기록을 Claim별로 연결한다.
6. `COMPLETED`와 `MATCH`를 서로 다른 상태로 취급한다.
7. 7단계 표현 정책에 맞춰 최종 답변을 구성한다.
8. Fact나 Evidence가 누락되면 `PARTIAL`·`UNANSWERABLE`·`FAILED`의 경계를 지킨다.

### 8.3 C의 후속 검수

역할 B가 결과를 반환하면 C는 다음을 확인한다.

- 8개 원문 정보가 정확한 행에서 추출됐는가?
- 원문값·단위·정규화값이 손실 없이 보존됐는가?
- 공시값과 재계산값이 구분됐는가?
- 연결재무제표 기준과 일정 주석이 누락되지 않았는가?
- 재계산 원값·반올림값·판정이 승인 정책과 같은가?
- 최종 문장이 투자 권유나 과도한 금융 판단을 포함하지 않는가?

## 9. 8단계 최종 패키지에서 확정할 항목

1. 정책 버전을 `1.0`으로 고정한다.
2. 역할 B의 실제 추출 결과와 이 문서의 기준정보를 비교한다.
3. 실제 Evidence locator 형식을 확정한다.
4. 실제 API·DTO의 상태명과 작업 용어의 매핑을 확인한다.
5. 치명적 오류 목록과 합격 조건을 확정한다.
6. A·B가 수용한 후 `C_APPROVED`로 상태를 변경한다.

## 10. 핵심 결론

이번 작업의 목적은 정답 문장 하나를 손으로 만드는 데 있지 않다. 대회 제공 원문에서 확인한 정보를 기준으로 다음의 유한한 계약을 만든 것이다.

```text
공시 원문 정보
+ 승인된 Fact 의미
+ 정규화 규칙
+ 승인된 계산식
+ 계산 가능 조건
+ 답변 상태 판정
+ Claim별 Evidence
+ 허용·금지 표현
= 백엔드가 반복 실행하고 검증할 수 있는 금융 도메인 골든 케이스
```

사용자 질문의 표현은 무한히 달라질 수 있지만, 역할 A는 질문을 승인된 의도와 Fact·계산 ID로 연결하고, 역할 B는 유한한 추출·계산 계약을 실행한다. 기존 계약으로 답할 수 없는 질문은 LLM이 새 계산식을 임의로 만들지 않고, 근거 부족 상태로 처리하거나 이후 정책 확장 후보로 등록한다.
