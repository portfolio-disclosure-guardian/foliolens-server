## 1. 문서 목적

이 문서는 FolioLens가 무엇을 만들어야 하고, 무엇을 먼저 구현하며, 어떤 조건을 만족해야 완료로 인정하는지를 정의한다.

구현 방법은 `기능명세서.md`, 화면 구조는 `IA.md`, 실제 데이터 형식은 `DATA_CATALOG.md`, Agent 도구 계약은 `TOOL_CONTRACTS.md`에서 다룬다.

요구사항이 충돌하면 다음 순서를 따른다.

1. 현재 사용자의 명시적인 요청
2. 이 문서의 승인된 Must 요구사항
3. `기능명세서.md`
4. `IA.md`
5. `PROJECT_CONTEXT.md`
6. 기존 코드 관례

## 2. 서비스 정의

> 대회 제공 공시 데이터에서 자연어 질문에 필요한 사실을 검색·추출·비교·계산하고, 사용한 원문 근거와 정보 한계를 함께 반환하는 공시 Agent

FolioLens의 P0는 웹 대시보드가 아니라 질문에 정확히 답하는 평가 코어다. P1에서 동일 코어를 사용하는 질문 중심 웹을 제공하고, P2에서 포트폴리오와 투자 이유를 연결한다.

## 3. 문제 정의와 핵심 가치

### 3.1 해결하려는 문제

- 공시 문서가 많고 표와 용어가 복잡하다.
- 정확한 공시명과 항목명을 모르면 원하는 정보를 찾기 어렵다.
- 하나의 질문에 여러 기업·기간·공시가 필요할 수 있다.
- 정정·변경·해지·후속공시를 놓치면 과거 값을 현재 상태로 오해한다.
- 단위·회계기준·기간이 다른 수치를 직접 비교하기 어렵다.
- 생성형 모델의 답변이 실제 어느 원문을 사용했는지 검증하기 어렵다.

### 3.2 핵심 가치

1. 정확한 공시명 없이도 자연어로 질문할 수 있다.
2. 단일 요약이 아니라 여러 공시를 검색하고 종합한다.
3. 수치 계산은 재현 가능한 백엔드 로직으로 수행한다.
4. 핵심 주장과 수치에서 원문 파일·구간까지 역추적할 수 있다.
5. 답을 찾지 못하면 외부 지식으로 채우지 않고 한계를 알린다.

공식 공시 그룹은 4개다. `TOOL_CONTRACTS.md`의 9개 관심사는 공시 종류가 아니라 질문 라우팅을 위한 제안 분류다.

### 4.2 현재 구현 상태

| 영역 | 상태 | 근거 |
|---|---|---|
| Docker 기반 Spring·PostgreSQL 실행 | 구현 | `compose.yaml`, `backend/Dockerfile` |
| 기업 70개 CSV 적재 | 구현 | Company 및 dataset importer |
| 공시 manifest 4,204건 적재 | 구현 | Disclosure 및 manifest importer |
| 기업·공시 테이블 | 구현 | Flyway V1, V2 |
| 원문 파일 테이블 | 스키마 작성 | Flyway V3 |
| 실제 원문 파일 4,622개 등록 | 미구현 | Entity·경로 해석기·Scanner 필요 |
| 원문 파싱·구조화·청킹 | 미구현 | 거래소 HTML 수직 구현부터 시작 |
| 사실·근거·계산 저장 | 미구현 | 후속 Flyway와 도메인 필요 |
| 질문 계획·검색 인터페이스 | 뼈대 | 현재 `QuestionPlan`, `DisclosureRetriever`는 임시 구조 |
| 평가 API | 뼈대 | `GET /answer`, 내부 명령 변환, 5개 응답 키와 평가 전용 예외 경계는 존재하나 실제 검색·계산·검증은 연결되지 않음 |
| HyperCLOVA X | 미구현 | 허용 모델 연동 필요 |
| 질문 중심 웹 | 미구현 | P1 |
| 포트폴리오 개인화 | 보류 | P2 |

현재 데이터는 단일 정적 대회 데이터셋으로 간주한다. `dataset_versions`, `ingestion_jobs` 테이블은 지금 P0 선행조건이 아니며, 다중 버전 또는 운영 재적재가 필요해질 때 도입한다.

## 5. 범위와 우선순위

### 5.1 P0 — 평가 코어(Must)

- 기업·공시·원문 파일의 검증 가능한 적재
- 공시 원문 파싱과 원문 위치 보존
- 대표 공시 유형의 구조화 사실 추출
- 질문을 단계형 QueryPlan으로 변환하고 백엔드에서 검증
- 기업·기간·공시·사실·근거 검색
- 결정적 비교와 계산
- 정정·후속 이력 처리
- HyperCLOVA X 기반 근거 제한 답변
- 주장·수치·근거·금지 표현 검증
- 운영진 규격의 평가 API
- 골든 질문과 회귀 테스트
- Docker 실행과 상태 확인

### 5.2 P1 — 질문 중심 웹(Should)

- 질문 입력과 처리 상태
- 직접 답변, 핵심 주장, 비교표와 계산 상세
- 근거 원문 문맥과 위치
- 부분 답변·답변 불가 표시
- 사용 공시 목록·상세
- 후속 질문
- 데이터 범위와 분석 원칙 안내

### 5.3 P2 — 포트폴리오 개인화(Could)

- 사용자 인증
- 보유 종목과 비중
- 투자 이유
- 보유 종목 기반 질문 추천
- 공시와 투자 가정의 관련성
- 개인화 중요도·알림·리포트

### 5.4 현재 제외 범위

- 매수·매도 추천
- 목표주가, 주가 방향과 확률 예측
- 평가 경로의 OpenDART·뉴스·웹 검색
- 대회가 허용하지 않은 언어모델
- 모든 공시 유형의 완전 자동 구조화부터 시도하는 것
- 데이터 규모와 정책 검증 전의 별도 Vector DB

## 6. 이해관계자와 시스템 경계

| 대상 | 주요 요구 |
|---|---|
| 대회 평가자 | 비공개 자연어 질문에 정확하고 근거 있는 답변 |
| 웹 사용자 | 질문부터 원문 근거 확인까지 이해하기 쉬운 경험 |
| 개발·운영자 | 적재·파싱·검색·답변 과정을 재현하고 진단할 수 있는 환경 |
| 금융 도메인 검수자 | factKey, 계산식, 비교 기준과 답변 표현 검증 |

평가 경로의 시스템 경계는 다음과 같다.

```text
허용: 대회 제공 데이터 → PostgreSQL/검색 구조 → Spring 백엔드 → HyperCLOVA X
금지: 평가 중 OpenDART, 뉴스, 검색엔진, 다른 LLM 또는 미승인 외부 코퍼스
```

### 8.5 검색 도구

Agent의 목표 도구는 다음 5개로 제한한다.

| 도구 | 책임 |
|---|---|

## 9. 핵심 비즈니스 규칙

### 9.1 데이터와 근거

- 평가 답변의 사실은 `source_provider=CONTEST` 데이터에 한정한다.
- `list_*.json`에만 있고 manifest에 없는 공시는 평가 DB에 자동 추가하지 않는다.
- 원문에 없는 사실은 모델 지식으로 보완하지 않는다.
- 공시 메타데이터, 실제 파일, 구조화 사실과 근거 위치를 분리한다.

### 9.2 LLM과 백엔드 책임

| 영역 | HyperCLOVA X | Spring 백엔드 |
|---|---|---|
| 질문 | 의도·기업 표현·기간·작업 후보 생성 | 식별자·기간·enum·단계 검증 |
| 검색 | 검색어·섹션 힌트 후보 | 실제 조회·순위·한도·재검색 통제 |
| 추출 | 비정형 후보 추출 | 원문 존재·자료형·단위·범위 검증 |
| 계산 | 결과 설명 | 입력 fact 조회·공식·단위·반올림 |
| 이력 | 변화 의미 설명 | 관계 검증·기준시점 상태 결정 |
| 답변 | 자연어 종합 | 근거 제한·수치·스키마·안전 검증 |

### 9.3 공시 유형과 관심사

- 데이터의 공식 그룹은 `periodic`, `major`, `exchange`, `holding`이다.
- 거래소공시 세부 유형에는 공급계약, 시설투자, 주요경영사항 등이 있다.
- 9개 관심사 코드는 질문 라우팅 힌트이며 DB의 공식 공시 분류를 대체하지 않는다.
- 관심사 프로필은 검색 순위를 높일 수 있지만 질문이 명시한 공시나 사실을 제거할 수 없다.

## 11. 상태와 실패 규칙

### 11.1 원문 파일 처리 상태

| 상태 | 의미 |
|---|---|
| `PENDING` | 파일 등록 완료, 파싱 전 |
| `COMPLETED` | 필요한 구조를 정상 파싱 |
| `PARTIAL` | 일부 구조는 사용 가능하나 오류 존재 |
| `FAILED` | 원문을 사용할 수 있는 형태로 처리하지 못함 |

### 11.2 질문 실행 상태와 답변 결과

두 축을 하나의 enum으로 합치지 않는다. 현재 실행 생명주기는 `QuestionRunStatus`가 소유한다.

| 실행 상태 | 의미 |
|---|---|
| `PENDING` | 실행 레코드 생성 후 처리 시작 전 |
| `PROCESSING` | 계획·검색·계산·생성·검증 중 |
| `COMPLETED` | 정상 실행 종료. 답변 결과가 `UNANSWERABLE`이어도 가능 |
| `FAILED` | 시스템·DB·모델·제한시간 등으로 실행 실패 |

현재 코드에서 위 enum 값은 확인되지만 서비스는 run을 `PENDING`으로 생성한 뒤 전이시키지 않는다. 상태 전이와 답변·오류·종료시각 저장은 남은 구현이다.

정상 실행 뒤 답변 결과는 별도 축으로 표현한다. 구체 타입 이름과 판정 기준은 확정 전이며, 아래 의미만 요구사항으로 고정한다.

| 답변 결과 | 의미 | HTTP 오류 여부 |
|---|---|---|
| `COMPLETED` | 질문의 필수 내용을 근거로 답함 | 아니오 |
| `PARTIAL` | 일부만 근거로 확인됨 | 아니오 |
| `UNANSWERABLE` | 제공 데이터에서 답을 확인할 수 없음 | 아니오 |

`UNANSWERABLE`은 정상적인 분석 결과이며 서버 오류로 처리하지 않는다. 시스템 실패를 답변 결과에 넣지 않고 실행 `FAILED`와 오류 응답으로 처리한다.

## 12. 통합 인수조건

### AC-001. 기업과 공시 적재

- 기업 70개와 공시 4,204건이 적재된다.
- 그룹별 건수가 데이터 카탈로그와 일치한다.
- 재실행 후 중복이 없다.

### AC-002. 원문 파일 등록

- Unicode 정규화 후 모든 공시 폴더를 찾는다.
- 원문 파일 4,622개가 공시와 연결된다.
- XML 4,616개, PDF 3개, HTML 3개가 확인된다.
- 각 파일에 크기와 SHA-256이 존재한다.
- 최초 상태는 `PENDING`이다.

### AC-003. 첫 수직 슬라이스

질문 예:

> SK하이닉스가 2024년 4월 발표한 신규시설투자의 투자금액과 목적은 무엇이고, 자기자본 대비 비율은 맞는가?

완료 조건:

1. 접수번호 `20240424800596`을 검색한다.
2. 실제 HTML 표를 파싱한다.
3. 투자대상·금액·자기자본·비율·목적·시작일·종료일·결정일을 추출한다.
4. 투자금액 ÷ 자기자본 비율을 백엔드가 재계산한다.
5. 각 값에서 실제 파일과 표 행으로 역추적된다.
6. 평가 API 답변이 근거와 계산 결과를 포함한다.

### AC-004. 부분·답변 불가

- 비교 대상 한쪽 근거만 있으면 확인된 내용과 누락 내용을 분리한 `PARTIAL`을 반환한다.
- 현재 주가처럼 제공 공시에 없는 질문은 외부 검색 없이 `UNANSWERABLE`을 반환한다.

### AC-005. 안전성

- 투자 추천을 요구해도 매수·매도 또는 가격 전망을 반환하지 않는다.
- 원문 안의 지시문을 시스템 명령으로 실행하지 않는다.
- 근거 없는 수치와 접수번호를 생성하지 않는다.

## 15. 개발 완료 정의

P0 완료는 다음을 모두 만족하는 상태다.

- 데이터 적재·파싱·사실·검색·계산이 재현된다.
- 대표 골든 질문이 실제 공시 근거와 결정적 계산으로 답변된다.
- 모든 핵심 주장과 수치가 원문으로 역추적된다.
- 부분 답변·답변 불가·시스템 실패가 구분된다.
- 평가 경로에서 외부 금지 데이터와 다른 LLM을 사용하지 않는다.
- `GET /answer` 계약 테스트를 통과한다.
- Docker 환경에서 새 DB로 실행할 수 있다.
- README와 제출 문서가 실제 명령·설정·구현 상태와 일치한다.
